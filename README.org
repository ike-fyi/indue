* Introduction

Indue is a markup language designed from scratch for outliner, task management, and personal knowledge management (PKM) use cases. It draws inspiration from Typst's syntactic sensibility and org-mode's productivity features.

The name "Indue" comes from the archaic English verb meaning "to put on as a garment", to clothe or endow something with qualities it did not previously have. Plain text puts on Indue and gains structure, tasks, tags, references, and hierarchy. Remove the markup and the text is still there, perfectly readable. This metaphor of equipping text with power runs through the entire language and its vocabulary.

Indue files are plain text. They are readable and writable in any editor without special tooling. The markup is lightweight enough that it does not obscure the content it describes.

* The Indue Specifications

Indue is specified across five companion documents. Each is complete on its own terms and can be read and implemented without the others open; cross-references between them are recommendations, not dependencies.

| Document                              | Covers                                              |
|---------------------------------------+-----------------------------------------------------|
| *Indue, Language Specification* (this) | Syntax, conventions, and the semantic model         |
| *The Indue Spellbook*                  | Every spell, by category, with its quirks           |
| *Indue Vault Specification*            | Multi-document collections: visibility, scoping, import and export |
| *Indue Query Syntax*                   | Finding and reading data, in SQL             |
| *Indue Reference Schema*               | The tables an AST maps onto, which queries address |

This document is what an implementer builds a parser against: the characters, the structures they form, and the rules that decide what a construct means. It defines the *mechanics* of spells (how they take inputs, where their effects land, how they compose) but not the catalogue of individual spells, which lives in the Spellbook.

The task and scheduling models are the exceptions, and deliberately so. Tasks and scheduling are the two reasons Indue exists, and their semantics are *guarantees* rather than vocabulary: a task's three lifecycle states, and the closed grammar of a recurrence pattern, are what let a document written in one application mean the same thing in every other. Guarantees belong with the language. The spells themselves, their inputs and their catalogue entries, live in the Spellbook.

Adding a spell is not a breaking change. Unknown spells recover forward by design (see Parse, don't fail), so an implementation built against an earlier version stays correct when it meets a spell it does not know.

** Glamours (inline formatting)

Each glamour is shorthand for a spell. A single glamour expands to the spell plus its wall; a pair brackets a rich target. Repeats collapse (~***~ is ~*~), and stacking different marks requires a bracket (~*/[text]~). See Glamours for the full rules.

| Character | Effect        | Spell equivalent |
|-----------+---------------+------------------|
| ~*~         | Bold          | ~:bold~            |
| ~/~         | Italic        | ~:italic~          |
| ~_~         | Underline     | ~:underline~       |
| ~%~         | Strikethrough | ~:strike~          |
| ~`~         | Code          | ~:code~            |

Superscript (~:sup~), subscript (~:sub~), and maths (~:math~, aliased ~:$~) are spells; they have no glamour character.

* Core Design Philosophy

** Prefer unambiguous syntax

Indue prefers syntax where every character's role is resolvable from local context. The parser should never need to look ahead through unbounded content or backtrack to determine meaning. Characters may appear in multiple roles (e.g. ~:~ opens a spell and terminates one), but context always disambiguates which role applies.

** Glamours are for frequent writing; spells are for transforms

The bar for earning a dedicated glamour is high: the feature must appear frequently enough in everyday writing that the ergonomic cost of a spell (function call) is genuinely burdensome. Anything that transforms content into a different form belongs in the spell system (~:func~). The glamour table is for things you type constantly.

** Bracket types replace quoting

No string literals with quote delimiters exist anywhere in Indue. Text is passed to spells using the appropriate bracket type: vessels ~()~ for values, scrolls ~[]~ for unparsed text, and conduits ~{}~ for rich parsed content. Quotes inside any bracket type are just literal characters.

** Every spell is useful in isolation

A spell that only makes sense composed with one specific other spell is a design smell. Those should be redesigned as a single spell with multiple ports. Each spell should carry clear meaning on its own.

** Same spell overwrites, different spells compose

When the same spell appears twice in a chain, the later instance wins. When different spells appear in a chain, they are additive:

#+begin_example
:color<red>.color<blue>:word    ; blue wins (same spell, later overwrites)
:bold.italic:word               ; both apply (different spells, additive)
#+end_example

** Single-column renderability

Indue defines no layout mechanism. A conforming application must be able to render any document in a single column without loss of meaning, so nothing in the core may require an application to place content side by side.

The test is practical: an outliner with a one-column interface has no way to understand a column instruction, and a construct some conforming applications structurally cannot render is worse than no construct at all, because it breaks the guarantee that every compliant application reads a document correctly.

Tables are the one exception, and they are not really an exception. A table is multi-column *internally* but occupies a single block-level slot, so a one-column application renders it as a unit (scrolling or wrapping as it sees fit) without understanding layout at all. The document's structure is identical either way. Mobile applications are encouraged to set breakpoints that collapse wide tables by default.

Presentational properties are fine, because they inset or decorate a block rather than arrange blocks relative to each other: margins, padding, ~:radius~, ~:border~, and ~:stroke-color~ all apply to tables and blocks without portability risk. An application that cannot round a corner simply does not, and the content still reads.

For genuine typesetting, page geometry, columns, page breaks, floats, export to Typst is the recommended path once tooling exists (see Relationship to Typst). A future version may revisit basic layout, but only for constructs that remain single-column viewable at every breakpoint.

A useful guide while the language is young: if Org-mode does not have it, Indue almost certainly should not have it yet.

** Spells are renderer-agnostic at core tier

Core formatting spells must have clear meaning regardless of rendering target (screen, print, plain text, accessibility). CSS-specific behavior belongs in the ~:ext.css~ extension namespace, not in core spells.

** Explicit targeting over implicit

Every scope level in Indue has an unambiguous syntactic form. A target is always a container, or a bare word glued to the right of a spell, never something inferred from position. Places are named by stations (~^name~), entities and type markers are targeted with ~<...>~, text through scrolls and conduits, and paired regions through shells. Whether an effect lands on text or on a block is decided by the spell's own nature, never guessed from context. A spell with no target paints its enclosing scope, which is a stated behavior rather than a guess.

Explicit targeting also gives failure a single answer. Because every spell has a target slot, an unrecognised spell degrades the same way regardless of what it was: drop the spell, render the target. A parser needs no per-spell knowledge of which part was meant to survive, which is what lets the vocabulary grow without ever breaking an older implementation.

** Scrolls and conduits are the default carriers

Most content flows through scrolls ~[]~ (unparsed) or conduits ~{}~ (rich parsed content). Vessels ~<>~ carry the values a spell computes with: a number, a date, a color, a setting, and become *targets* when marked with ~@~ or ~&~. Parentheses are deliberately unreserved, a parenthetical in prose must stay a parenthetical. When designing a spell, reach for scrolls or conduits first; use vessels only when the input is a specific ingredient the spell needs to evaluate. Since ~[~ and ~{~ share the same physical key, muscle memory stays simple.

** Names public, behavior private

Indue's visibility defaults follow a single principle: *names need to be findable, behavior needs to be opt-in*. Entities (sigils, signets, stations) are vault-public by default because a name that cannot be resolved is useless. Configuration (codexes, schemas, satchel-hosted spells) is file-local by default because shared styling is a deliberate choice, silent cross-file styling is a debugging nightmare. The beacon (~!~) is the single mechanism that promotes a private codex to the vault's public layer; everything else follows from these two defaults.

** Logical scope, OS-enforced security

Indue declares /logical/ scope, what is visible to what, where names resolve, how the public layer composes. It does not enforce access control. Filesystem permissions, ACLs, encryption, and sandboxing are the OS's domain and operate on Indue files as on any plain text. Tools should be permission-aware (handle failures gracefully, surface them clearly) but never attempt to duplicate security in markup.

** The nick (~\~)

~\~ is reserved as an escape character. Its primary use is rendering a literal glamour character that would otherwise be interpreted as markup:

#+begin_example
The price is 50\% off       ; literal %, not strikethrough
Use \*asterisks\* literally ; literal *, not bold
#+end_example

~\~ before a non-glamour character renders as a literal backslash.

** Parse, don't fail

Indue parsers should never throw errors at the user for malformed markup. Unclosed glamour delimiters apply to the single word they touch (single-word rule), or render as literal text if not touching a word. Unknown spell names render their content as plain text. The no-errors philosophy follows HTML's error recovery model rather than Typst's strict compilation model.

Strict validation belongs in the linter and export pipeline, not in the core parser that runs while someone is writing notes at midnight.

** Recover forward

Parse-don't-fail is the floor: the parser never throws an error at the writer. This principle is the ceiling built on top of it. In Indue the absence of a referent is a *first-class state, not an exception*. "Not yet resolved," "not yet known," and "not yet defined" are legal, meaningful, and frequently useful conditions rather than degraded ones. An unresolved signet still carries meaning and upgrades itself the moment its target appears. An unknown spell renders its conduit as rich content, so a future spell and a not-yet-known one produce coherent output today. A station with no sibling is still a navigable anchor. A cauldron may target an entity that does not exist yet and simply activates when it does. This is what makes incremental, out-of-order authoring, thinking of a tag before defining its behavior, referencing a person before making their page, sketching a trail before its stops exist, feel native to Indue rather than error-prone. This is closer to how a spreadsheet treats a reference to an empty cell (a real value you can build on) than to how a compiler treats an undefined symbol.

Because these fallbacks are the same primitives resolving differently, not ad-hoc repairs, their results are *legible*: a surprising outcome is a combination the writer can understand and then reach for on purpose. And a feature's default is continuous with its advanced form, so the writer enters at the zero-config end of a ramp they did not know was a ramp. Three identically named stations cycle as a trail on their own; discovering that cycle leads directly to ~| n~ ordering and the ~| x~ terminator, the same construct one parameter further along:

#+begin_example
^argument          ; three of these auto-cycle: an undefined trail
^argument
^argument          ; look it up, and the fix is the same construct, ordered:
^argument | 1
^argument | 2
^argument | x      ; ordered, terminated. the accident taught the feature.
#+end_example

The default is the on-ramp to the depth. Investigating "what actually happened" tends to level the writer up rather than send them back to a wall. The mistakes are the tutorial.

This principle *raises* the specification bar rather than lowering it. A behavior discovered in one application must be the behavior every compliant application produces, and "look it up" must terminate in a documented answer, otherwise an accident is merely a bug that has not recurred yet. Every fallback path is therefore defined behavior, specified to the same rigor as the success path. Determinism is what turns a happy accident into a feature; cross-application agreement is what makes it worth learning. The permission to play is earned by pinning down exactly what play does.

* Vocabulary

Indue uses a thematic vocabulary inspired by RPG and medieval conventions to name its syntactic concepts. These names are optional, the common markup names are always valid and appear alongside the Indue terms throughout this specification. The thematic vocabulary exists to make the concepts memorable, teachable, and distinct from other markup languages.

The core metaphor: plain text is your base character. Indue is the gear system. You equip your text with markup and it gains new abilities. Strip the gear off and the character is still there, still whole.

| Syntax         | Indue name | Common name          |
|----------------+------------+----------------------|
| ~-~, ~+~, ~=~        | *Socket*     | Structural marker    |
| Node created   | *Slot*       | Block / node         |
| ~*~, ~/~, ~_~, ~%~      | *Glamour*    | Inline formatting    |
| ~#~              | *Sigil*      | Tag                  |
| ~@~              | *Signet*     | Reference / mention  |
| ~:fn~            | *Spell*      | Function             |
| ~.~              | *Bond*       | Spell chain operator |
| ~::~             | *Shell*      | Region effect, length-matched |
| ~:::~ and longer | *Hypershell* | Content-safe region           |
| ~<>~             | *Vessel*     | Value argument           |
| ~@<>~            | *Summons*    | Targets one spell in a chain |

| ~()~             | *Vessel*     | Value argument       |
| ~[]~             | *Scroll*     | Verbatim block       |
| ~{}~             | *Conduit*    | Rich content block   |
| ~^label~         | *Station*   | Anchor (a named place)       |
| ~&name&~         | *Source*    | Canonical record for a name  |
| ~\~              | *Nick*       | Escape character     |
| ~\~~             | *Satchel*    | Hoisted config block |
| Config block   | *Codex*      | Inherited properties |
| ~!~              | *Beacon*     | Public marker        |
| ~;~ / ~;;~ / ~;;;~ | *Whisper*  | Comment              |
| ~[label](url)~   | *Goety*      | Borrowed familiar shape |
| ~[]~             | *Void*       | A value-shaped absence   |
| (positional)     | *Spell block* | A block rendering only one spell's target |

A one-sentence summary of the entire system: sockets create slots; glamours, sigils, signets, and spells equip the content sitting on those slots; bonds chain spells together; shells open paired scopes with independent termination; vessels carry values, and become targets when summoned; scrolls, and conduits carry data between them; and beacons promote private codexes into a vault's public layer. Codexes configure how glamours, sockets, and entities bestow their properties; styling follows rendering, an a spell's nature decides whether it paints a block or a span, and sigils, signets, and stations style their rendered expressions.

* Inspirations

** Typst

Typst is a modern typesetting language with a clean, consistent syntax. Indue borrows directly from it:

- Bold (~*text*~) and the general aesthetic of lightweight paired delimiters.
- List markers (~-~ for unordered, ~+~ for ordered).
- Heading syntax (~=~ / ~==~ / ~===~).
- Labels (~^label~) and references (~@ref~).
- The principle that functions and evaluation should have a clear, single prefix character.

Where Indue parts ways with Typst:

- Typst reserves ~#~ for function calls. Tags, one of the most natural and important constructs in PKM, require a function call like ~#tag("work")~. Indue reclaims ~#~ for native tag syntax and moves functions to ~:~.
- Typst has no built-in concept of tasks, checkboxes, or task states. These must be added through packages and show rules. Indue makes them native.
- Typst is a strict compiler: malformed input is an error. Indue follows an HTML-style error recovery model where malformed markup renders as literal text rather than failing.

** Org-mode

Org-mode is the most powerful plain-text outliner and task system in existence, but its spec and runtime are so entangled with Emacs that every non-Emacs implementation is permanently incomplete. Neovim and Helix users are permanently second-class citizens.

Indue borrows the /idea/ that tasks, scheduling, and metadata belong in the markup itself. It does not inherit Org's property drawers, babel blocks, or export dispatcher. More importantly, Indue is deliberately designed to be fully and correctly implementable by anyone, a Rust reference CLI, a tree-sitter grammar, and a clean formal spec mean that any editor gets first-class support from day one, not as an afterthought.

** CommonMark

Indue is not trying to be CommonMark. CommonMark is purely presentational with no opinion about what content /means/. Indue is positioned between CommonMark and Org-mode: richer than CommonMark in semantic content (tasks, tags, entities, scheduling), simpler and more portable than Org-mode, and without Org's assumption of a specific runtime.

** Everyday conventions

- ~#~ as tag comes from social media and is universally understood.
- ~:~ as function/evaluation is lightweight and familiar from emoji shortcodes, YAML keys, and general programming conventions.

* Spells: The Core Mechanic

A *spell* is a named transform. Everything in Indue that changes how content looks or behaves is a spell, including the shorthand forms (glamours) that never spell out a name. Learn this section and the rest of the language is mostly vocabulary.

** What spells do

Spells have three kinds of effect, and one spell may have any combination:

1. *Styling*. Changing appearance (~:bold~, ~:span-bg~, ~:card~).
2. *Data*. Attaching machine-readable meaning (~:due~, ~:x~, ~:info~).
3. *Embedding*. Producing content at the spell's position (~:link~, ~:table~, ~:query~).

A spell's *name* is letters, digits, and hyphens. Two names may refer to the same spell (~:fg~ and ~:color~ are aliases).

*** The categories do most of the work

These three are not a taxonomy for its own sake. Nearly every rule that could have been a special case turns out to be one of the categories behaving as it must, so it is worth having them in mind before reading the rest.

| Behaviour                          | Styling            | Data                | Embedding             |
|------------------------------------+--------------------+---------------------+-----------------------|
| With no target                     | paints the enclosing scope | sets a property on the block | generates its own target |
| Trailing whitespace                | eaten, if untargeted | eaten, if untargeted | kept: content fills the position |
| On an astral block                 | aliases the enclosing scope's property | sets the astral block's own property | promotes the block to material |
| Reach                              | block deep, span shallow | not applicable   | applies to the generated content |

Where the astral row meets the embedding column is what makes astral blocks work at all: a block is astral because it has no rendered content, so the moment something embeds into it, it stops being astral. Nothing needs to say so separately.

That same row is why property storage is uniform. Every block has the same property table, astral or not; only the *styling* properties differ, and on an astral block they are aliases into the enclosing scope rather than values of their own. Data properties are local on every kind of block, which is what lets metadata sit on something invisible.

** Spell world

Indue text is either *material* (ordinary content you read) or *spell world* (syntax the parser reads). Knowing where spell world begins and ends is the whole of the grammar.

*** Entering

Three things open spell world:

- The *wall* ~:~, followed by a spell name or a container.
- A *container* in leading position: ~<~, ~{~, or ~[~.
- A *bond* ~.~ continuing an open chain onto a new line.

#+begin_example
:bold:word                 ; opened by the wall
<=>.bold                   ; opened by a vessel, no wall needed
{rich content}.quote       ; opened by a conduit
[unparsed text].code       ; opened by a scroll
#+end_example

Parentheses are *not* part of spell syntax. They are far too common in ordinary prose to read structurally, so they belong entirely to the writer.

*** Leaving

Three things close a spell construct:

- *Whitespace* outside a container. Spell names cannot contain spaces, so a space always terminates.
- *A line break* outside a container, unless the next line continues the chain.
- *The closing wall* ~:~, written explicitly.

#+begin_example
:span-bg<red>.bold:word    ; the wall closes it
:span-bg<red>.bold word    ; the space closes it; "word" is ordinary text
{a}.span-bg<red> .bold     ; the space ends it; ".bold" prints as text
#+end_example

**** Line breaks in detail

A line break is the one terminator with cases, because it is where a construct may continue rather than end. Four rules cover it:

1. *Inside a container, a line break ends nothing.* A scroll or conduit that spans lines keeps its construct open, and its contents are unaffected. This is what lets a multi-line code scroll or a rich conduit sit inside a spell without breaking it.
2. *Outside a container, a line beginning with a bond continues the chain.* The construct is still the same construct.
3. *Outside a container, a line beginning with a wall starts a fresh construct.* Whatever preceded it is closed, whether or not it looked finished.
4. *Anything else ends the construct.* The next line is ordinary content.

#+begin_example
:code[fn main() {
    println!("hi");
}]                         ; rule 1: the scroll spans lines, nothing ends

:span-bg<red>
.bold
.underline:                ; rule 2: bonds continue the chain

:repeat[every week on thursday]
:after<completion>
:completions<>             ; rule 3: each wall starts a new construct
#+end_example

The third case is worth noticing for how it reads. Stacking constructs on their own lines gives a block a drawer-like appearance, one property per line, without any drawer syntax existing: these are ordinary spells, laid out.

**** Chaining and consecutive constructs are not the same thing

~:a.b~ and ~:a~ followed by ~:b~ currently produce identical results, because the fold accumulates the same properties either way.

They are not, however, the same construct, and the equivalence should not be relied on. A future spell that reads what preceded it within its own chain would distinguish them. Implementations must not normalise one form into the other, and documents should not assume they are interchangeable.

The end of a *block* is not a terminator. A block boundary bounds an effect's reach (see Scope), but there is no end-of-block inside a spell.

*** Walls are optional where the shape is already unambiguous

A leading container opens spell world by itself, so the wall is usually unnecessary. These three are identical:

#+begin_example
<target>.spell<input>
:<target>.spell<input>
:<target>.spell<input>:
#+end_example

Write the wall when you want it: mid-word, where no whitespace precedes the construct, or simply for clarity. ~:<~, ~:{~, and ~:[~ are shapes ordinary prose never produces, which is what makes mid-word application possible:

#+begin_example
16:[th].sup:               ; superscript on part of a word
#+end_example

A useful habit: when doing something uncommon, lead with the wall. It costs one character and puts you and the parser in the same frame of mind.

** Spell shapes

A construct is a sequence of *spell slots* separated by bonds. What goes in a slot decides what it does, and the order of slots is mostly free, so the same effect can be written more than one way.

These are *shapes*, in the sense a guitar chord has shapes: different fingerings of the same chord. Nothing about them is a separate rule, and the parser does not distinguish them. They are worth naming because they read differently, and because knowing both means never having to reorder what you have already written.

*** Spell slots

A slot is what sits between two bonds. Three kinds:

| Slot                | Is                                        |
|---------------------+-------------------------------------------|
| ~spell~ or ~spell<in>~  | An effect, acting on the construct's targets |
| ~<x>~, ~[x]~, ~{x}~     | A *construct target*                      |
| ~spell@<x>~           | An effect acting on that target alone     |

Every slot is self-contained: it carries its own spell, its own inputs, and its own target if it has one.

*** The cast shape

Spell first, target last. This reads as an instruction: do this, to that.

#+begin_example
:bold.{this text}
:span-bg<yellow>.radius<4>.{a highlighted passage}
#+end_example

Written out fully, with several spells, several targets, and an explicit closing wall:

#+begin_example
:spell1.spell2.{target}.<target>.[target]:
#+end_example

*** The offering shape

Target first, spells last. This reads as a transformation: take this, and do these things to it.

#+begin_example
{this text}.bold
{
- tip one
- tip two
}.smart-tips
#+end_example

A leading container opens spell world by itself, so no wall is needed. Written out fully, with the optional wall:

#+begin_example
:{target1}.<target2>.spell1.spell2:
#+end_example

*** Which to reach for

The cast shape suits knowing what you want before you write the content: styling a word mid-sentence, applying a known effect.

The offering shape suits having the content already: you wrote the list, and now you want it themed. It is also what makes a class read well at the call site, since the content leads and the name follows.

Neither is more correct. Most documents use both, in the same paragraph, without anyone noticing.

*** Interleaving is legal but not idiomatic

Because a bonded container is a construct target wherever it appears, and every unslotted spell acts on every construct target, these are identical:

#+begin_example
:{target1}.<target2>.spell1.spell2:
{target1}.spell1.<target2>.spell2
#+end_example

The second is valid and produces the same result. It is not written that way in practice, because separating spells from targets is what makes a long construct readable. Position carries no meaning, so there is nothing to gain by mixing them.

** Targets

A *target* is what a spell lands on. Every spell resolves one, or paints its scope if it has none.

*** Three positions, three meanings

Where a container sits, and whether it is glued or bonded, decides its role.
These three are distinguished lexically, with no lookahead:

| Form         | Role                                     |
|--------------+------------------------------------------|
| ~:spell<x>~    | *Input*, glued to the spell name         |
| ~:spell.<x>~   | *Target of the whole construct*, bonded  |
| ~:spell@<x>~   | *Target of that spell alone*, marked     |

A container opening the construct is bonded to nothing before it, so it is
also a construct target:

#+begin_example
<@alice>.bold              ; leading container: a construct target
:bold.<@alice>:            ; bonded container: the same thing
#+end_example

Position is otherwise not significant. A bonded container is a construct
target wherever it appears, and several accumulate:

#+begin_example
:bold.<a>.<b>:             ; bold applies to both a and b
:bold.<a b>:               ; the same, preferred
#+end_example

Examples in this specification put construct targets first or last, because
that reads best, but the rule does not require it.

*** The grab rule: a bare word to the right

A bare, unbracketed word *glued to the right of a spell* is taken as that
spell's target. This is a special phenomenon, and the only place an
undelimited target is recognised:

#+begin_example
:bold:word                 ; "word" is the target
:bold: word                ; the space closes the spell; nothing is targeted
#+end_example

It works only to the right, and only glued. Every other target is delimited
by a container, which carries its own boundaries and can therefore sit
anywhere. A bare word has no brackets, so the only position where its
boundaries are knowable is immediately after the spell, running to the next
whitespace. Leftward there is no signal at all: ~word:bold~ cannot be
distinguished from ordinary prose. A bare word can never be bonded either,
since ~.word~ is indistinguishable from the next spell in the chain.

This one rule is what makes the terse glamour forms possible (see Glamours).

*** Sub-spell targets (~@~)

A bonded container is a target of the whole construct. To give *one slot* its own target, glue ~@~ to the spell:

#+begin_example
<@>.bold.color<green>@<@nancy>
#+end_example

~@~ confines a slot's *direct* effect to its own target. It says nothing about what other slots do.

So in that example: every signet in scope goes bold, because ~.bold~ has no target of its own and takes the construct's. Nancy goes green, because ~.color<green>~ names her directly. And Nancy is also bold, because she is a signet and the construct's target set covers her.

Nothing is subtracted. A marked slot narrows what *it* does, not what reaches its target.

The difference from a plain bond is what happens to everything else:

#+begin_example
<@>.bold.color<green>.<@nancy>   ; Nancy joins the construct's targets
<@>.bold.color<green>@<@nancy>   ; only .color<green> acts on Nancy directly
#+end_example

In the first, ~.bold~ and ~.color<green>~ both act on every signet *and* on Nancy. In the second, ~.color<green>~ acts on Nancy alone, while ~.bold~ acts on the signets, Nancy among them.

*** A marked slot is scoped like everything else

~@<nancy>~ resolves within the construct's own scope. It reaches no further than the construct could: it narrows within what is already available rather than widening.

#+begin_example
:bold.color<green>@<nancy>.<#>:
#+end_example

Sigils go bold, since ~.<#>~ is the construct target. Nancy goes green if she is in scope. Nancy is not bold, because she is not a sigil.

*** Where this is actually for

Sub-spell targeting is uncommon in ordinary writing. Its purpose is letting a *compound spell reach its own internal parts*, which is what makes a class a theme rather than a style.

#+begin_example
<:smart-tips>
.card
.bg<#f0f7ff>
.border-color<#5b8def>
.bold@<=>
.span-bg<#fff3cd>@<#>:
#+end_example

At the call site that is one word:

#+begin_example
{
- tip one
- tip two
}.smart-tips
#+end_example

The block is framed and tinted, headings inside it are bold, tags inside it are highlighted. Without ~@~, a class could only set properties on the thing it was applied to, never on what that thing contains.

With only one spell in a construct there is nothing to narrow, so the two forms coincide:

#+begin_example
:upper.<:code>:            ; identical
:upper@<:code>:            ; identical
#+end_example

Adjacent summons on one spell are additive; the single-vessel form is preferred:

#+begin_example
:spell@<a>@<b>.spell2:     ; additive
:spell@<a b>.spell2:       ; preferred, same meaning
#+end_example

*** Reach

A block spell reaches the block *and everything it owns*, because a block encloses its subtree. A span spell reaches only its own run, because a span encloses nothing.

Those defaults serve the usual case: a card frames a heading and its body, and bolding a heading does not bold the paragraphs beneath it. Where the default is wrong, ~:deep~ and ~:shallow~ set reach explicitly.

#+begin_example
<=>.bg<red>.radius<8>.shallow:     ; a banner on each heading, not its body
#+end_example

Reach is ordinary property state, so position in the chain does not matter: the construct settles before anything renders, and a later write shadows an earlier one. That is what lets the correction be appended when a render turns out wrong, rather than inserted at the front.

The bare form sets both tiers; naming one (~:deep<block>~, ~:shallow<span>~) leaves the other alone.

*** Telling a target from an input

The rules above are the mechanism. For writing, a simpler intuition usually settles it: *if it is something you read in the finished document, or the thing holding what you read, it is a target. If it is instruction for the spell, it is an input.*

#+begin_example
:span-bg<yellow>:word      ; you read "word" (target); never "yellow" (input)
:code<rust>[body]          ; you read the body; "rust" only tells the spell how
#+end_example

Colours, sizes, dates, languages, and settings are inputs. Text, blocks, and references to either are targets.

** Scope: where the effect lands

| Target       | Scope                                            |
|--------------+--------------------------------------------------|
| ~:spell:word~  | the glued word, unparsed                         |
| ~[unparsed]~   | unparsed content, nothing inside is syntax        |
| ~{rich}~       | rich parsed content (nests)                      |
| ~<reference>~  | a value or reference (entity, marker, station)  |
| none           | the enclosing scope, painted forward             |

*** Generated targets: embedding spells

An embedding spell (~:link~, ~:embed~, ~:popover~, ~:query~) does not find a target, it *generates* one. Read it as though the spell supplied its own content in the target position:

#+begin_example
:link[url]                 ; behaves as :link[url]:{the generated link}
#+end_example

This is ordinary targeting with the target supplied rather than found, so everything follows from it: the spell's other effects apply to the generated content (~:link[url].bold~ bolds the link it produced), and that content occupies the position, which is why embedding spells do not consume trailing whitespace.

A target that resolves to text and carries no chain is therefore an embed:

#+begin_example
<embed-1>                  ; if embed-1 holds text, that text renders here
#+end_example

If the value is not text, nothing embeds, which is what distinguishes values usable as configuration from values usable as content.

*** No target: painting forward

A spell that resolves no target applies its properties *from that point to the end of its enclosing scope*, the way a fill tool floods to the boundary of a shape:

#+begin_example
Regular text :serif and everything after this in the block is serif.
#+end_example

So a spell at the start of a block paints the whole block, because there is nothing before it to leave alone. There is no separate positional rule for this; it falls out of having no target:

#+begin_example
:card                      ; untargeted, so it paints the block
#+end_example

This is especially useful inside lists, where content length may change:

#+begin_example
- = Project Alpha
  - :bold This item is bold regardless of how long it gets
  - Normal item
#+end_example

An untargeted spell cannot outlive its scope: it ends at the block boundary, so it needs no explicit closer. A property applies until shadowed by a later write to the same property, after which the earlier spell has no remaining observable effect.

*** Astral blocks

A block with no rendered content is *astral*. A spell sitting between blocks occupies one, and it is invisible in the render.

Astral is a *state*, not a kind of block. Structurally an astral block is an ordinary block with the ordinary property table; what differs is only how each effect category behaves on it, and that follows from the categories rather than from any rule about astral blocks:

- *Styling* properties are aliases into the enclosing scope's properties. Writing one on an astral block therefore sets the scope's default from that point, which is what paint-forward looks like from the inside:

#+begin_example
:serif                     ; astral; serif is the default from here on

= A heading
Body text, now serif.
#+end_example

- *Data* properties are local, as on any block. This is what makes an astral block useful rather than merely invisible: metadata does not need something visible to sit on.

#+begin_example
- :o Water plants :repeat[weekly].after<completion>
:completions[2026-04-07 2026-04-14]
#+end_example

- *Embedding* promotes the block. Content now renders there, so the block is no longer astral. Nothing needs to state this separately: astral is defined by having no rendered content.

An astral block is a real node in the document tree, not a parsing convenience. Its position is semantically meaningful, since moving one changes what its styling properties alias. Applications may surface astral blocks for visibility, folding, or navigation, and should treat their position as significant when offering reordering.

*** Spell blocks

A *spell block* is a block whose only rendered content is the content of one spell's target. The spell does not sit alongside other content in the flow; what it renders *is* the block.

#+begin_example
:code<rust>[fn main() {
    println!("hi");
}]
#+end_example

The test is about *rendering*, not about how the source is shaped. A construct with arbitrary structure nested inside its target is still a spell block, because the target's content is all that renders:

#+begin_example
:quote.{
:card.{To be, or not to be}
by Shakespeare
}:
#+end_example

Content that renders *beside* the spell breaks it. Here the code is one part of a block's flow, so it is not a spell block:

#+begin_example
:code[git status] shows the current state.
#+end_example

Whitespace inside the block counts as content for this test, even though it renders as nothing distinctive. A trailing space is therefore an escape hatch: it keeps a spell from constituting its block without putting anything visible next to it. Material *outside* the block, a following whisper or a blank line, is not part of the block and does not affect the test.

An astral spell renders nothing at all, so it is never a spell block. Declarations (cauldrons, satchels) contribute no rendered content either, and are likewise not candidates.

**** What spell blocks are for

Spell blocks exist so that shipped defaults *can* distinguish the two positions where convention expects it. Most spells render identically either way: ~:bold~, ~:color~, ~:link~, and ~:span-bg~ have no reason to care. A handful, code and maths in particular, are conventionally set apart with margins when they stand alone, and inline when they sit in a sentence.

That difference is presentation, so it belongs in configuration rather than in the spell. The position is a fact the language makes available; which spells use it, and how, is a default an application ships and a document may override.

Selector syntax for naming this position (a rule that applies to a spell only when it forms a spell block) is not yet settled. See Open Design Questions.

*** Trailing whitespace elision

A spell with no target consumes one trailing whitespace character if present, so purely functional spells leave no gap:

#+begin_example
He said :anchor and walked off.
   ;  renders "He said and walked off." with single spacing
#+end_example

Two spaces leave one behind. Embedding spells are the exception, and for the reason the category table gives: their generated content occupies the position, so there is no gap to close.

** Inputs

An *input* is data a spell computes with. Inputs are always *glued* to the spell name, which is what distinguishes them from targets.

- ~<a b c>~. A *vessel*: a space-separated argument list.
- ~[string]~. A *scroll*: a single unparsed string.
- ~{rich}~. A *conduit*: rich parsed content, for the uncommon case where a spell consumes content it will render somewhere other than the flow.

#+begin_example
:span-bg<red>              ; one argument
:mix<red 50%>              ; two arguments, space-separated
:shadow<2 2 4>             ; three arguments
:code[fn main() {}]        ; a single unparsed string, no quotes needed
#+end_example

*** Arguments inside a vessel

Arguments are separated by whitespace, following the same convention as CSS value lists. Each may be:

- a *literal* recognised by shape (~2~, ~50%~, ~#f0f0f0~, ~2cm~),
- a *reference* by sigil (~^wp~, ~#tag~, ~@person~),
- a *keyword* from the spell slot's vocabulary (~red~, ~center~, ~serif~),
- a *spell name* referenced rather than invoked (~:bold~ in ~:strip<:bold>~),
- a *quoted string* (~"a b"~ or ~'a b'~, equivalent, single-line),
- or an *unparsed string scroll* (~[a b]~).

A value containing spaces must be quoted or scrolled so its whitespace is not read as an argument boundary:

#+begin_example
:font<"Helvetica Neue" Arial>     ; quoted
:font<[Helvetica Neue] [Arial]>   ; scrolled, no quotes needed
#+end_example

*** The spec defines slots, not vocabularies

A spell's *slots* are specified: how many inputs it takes, of what kinds, in
what order. The set of *values* meaningful in a slot often is not, and this
is deliberate.

Some vocabularies are closed and can be enumerated, because they are finite
and every application can implement all of them: ~:align<center>~,
~:pattern<solid>~. Others are open-ended and belong to the application:
~:code~'s language is the clearest case. Which languages an application can
highlight depends on the grammars or language servers it happens to have,
that list churns constantly, and no specification can track it without going
stale or making applications non-compliant for not supporting a language
invented last year.

So the specification says ~:code~ takes a language input. It does not say
which languages exist. An application that does not recognise a value
renders without it, the same way an unrecognised spell degrades to its
target: one recovery principle, applied at both levels.

#+begin_example
:code<rust>[fn main() {}]  ; highlighted where Rust is supported,
                            ; plain monospace where it is not
#+end_example

This is also why language shortcuts are user-defined rather than built in. A
spell per language would commit the specification to a list it cannot
maintain, and would need revising every time a language appeared. Defining
one is a single line:

#+begin_example
<:rust>.code<rust>:        ; now :rust[...] is a Rust code block
#+end_example

The naming mechanism belongs to the language; the vocabulary belongs to
whoever is writing.

*** Commas are accepted

A comma between arguments is treated as whitespace, so ~<2, 2, 4>~ and ~<2 2 4>~ parse identically. This exists so habits carried from CSS or other languages do not produce errors. Space separation is the documented form.

*** How many containers

A spell takes at most *one container of each kind*: one vessel, and one scroll or conduit. Because the kinds are distinct, the parser identifies each by its brackets rather than by position, so *order is free*:

#+begin_example
:spell[string]             ; scroll alone
:spell<a b>                ; vessel alone
:spell<a b>[string]        ; vessel and scroll
:spell[string]<a b>        ; identical, order is free
#+end_example

Two containers of the same kind are invalid, since nothing but position would distinguish them. A list of same-kind values belongs inside one vessel. A scroll and a conduit are mutually exclusive: a spell consumes content either unparsed or parsed, not both.

*** Conduits as inputs

A conduit input is uncommon and deliberately so. Most rich content a spell touches is content the spell *acts on*, which makes it a target. The test is what should happen when the spell is dropped:

- If the content belongs in the readable document either way, it is a *target*. Table rows are the clear case.
- If it was only ever going to render somewhere other than the flow, it is an *input*. A popover panel is the clear case.

A conduit input is parsed as rich content. What the spell does with it afterward is the spell's business: one needing plain text flattens it. No separate cast-to-literal mechanism is needed.

*** Scrolls are unparsed, not verbatim

A scroll says one thing: *treat everything inside as text, not as special characters or spells.* Indue's grammar stands down. No spell fires, no glamour fires, no sigil or signet resolves, no bracket is read as a container. Characters that would otherwise be syntax are just characters.

#+begin_example
:font[Helvetica Neue]      ; the space is part of the name, not an argument break
:link[https://x.com/a#b]   ; # is a literal character, not a sigil
^[my long name]            ; a multi-word station name
[*not bold* and #nottag]   ; every mark here is ordinary text
#+end_example

That is the whole of it. A scroll makes *no presentational claim at all*, in either direction. It does not request monospace and it does not strip styling: content inside a scroll is styled exactly as the surrounding context already styles text. In a heading it looks like heading text; in a list item, like list text; in a paragraph, like paragraph text.

This is a deliberate departure from what "verbatim" means in most markup languages, where the term bundles two claims together: parsing is suppressed *and* the result is visibly marked as a literal reproduction, usually monospaced and set apart. Org's own description makes the visual claim explicit, calling it text styled to show the reader it is a literal reproduction.

Indue splits those. The parsing guarantee is the scroll, available anywhere and carrying no styling. The visual assertion is a spell:

| Construct     | Parsing        | Presentation                       |
|---------------+----------------+------------------------------------|
| ~[...]~ scroll  | unparsed       | none; inherits its context         |
| ~:code[...]~    | unparsed       | monospace, and *means* "this is code" |
| ~:mono[...]~    | unparsed       | monospace, no semantic claim        |

The split is what makes scrolls generally useful. If a scroll implied monospace, it could not carry a font name, a URL, a file path, a station label, or an emoji, all of which need the parser to stand down while looking like ordinary text. Because the guarantee is purely about parsing, a scroll is the general escape hatch: reach for it whenever text contains characters Indue would otherwise claim.

** Chains: the bond (~.~)

The bond ~.~ chains spells. Each adds its effect to the same construct.

#+begin_example
:bold.underline:word              ; bold + underline
:span-bg<red>.opacity<0.5>        ; two spells with inputs
#+end_example

Bonds connect spell names only. Inputs glue to their own spell, with no bond between a spell and its input.

*** A chain is an ordered fold

There is no separate category of "modifier" spell and no arithmetic inside vessels. A chain is an *ordered fold over property state*: each spell acts on the current value of the property it governs, left to right.

#+begin_example
:color<red>.mix<blue 50%>         ; red, then mixed halfway to blue
#+end_example

Order therefore carries meaning. Reversing that chain produces a different result.

*** Resetting properties (~:strip~)

~:strip~ resets inherited properties on its target to the application's defaults for that object type. Bare, it resets everything; with an argument it narrows to a single property:

#+begin_example
:italic.bold.{we will unbold [this].strip<:bold>}:
#+end_example

The outer chain sets italic and bold across the whole target. The inner scroll carries its own chain, ~.strip<:bold>~, which clears just the bold property for that word, leaving it italic-only while the rest of the passage stays bold and italic.

The argument is a *referenced* spell name, not an invocation, the same way ~:cycle<new selected processing>~ references state names as vessel values.

*** A note for readers coming from CSS

The bond does the job CSS gives to ~;~. Two differences are worth knowing.

The chain is an expression, not a statement list confined to a block. The same chain can be applied inline to a target, opened as a shell, stored as a named spell, or laid out vertically as a configuration block. CSS has one site for a declaration list; Indue has several, all using the same syntax.

And order carries more weight. In CSS, declaration order matters only for duplicate properties. Here a chain can be a pipeline.

** Multiline chains

A chain may break across lines. Whitespace and newlines *inside an open chain*, while consecutive lines keep starting with the bond ~.~, are insignificant:

#+begin_example
hello :spell
.spell2
.spell3:my dudes
#+end_example

renders as ~hello my dudes~ with the chain applied to "my dudes". Line breaking is purely how the chain is written; it does not change scope. A continuation line begins with ~.~, and this only reads as continuation while a chain is open, so a leading decimal or an ellipsis in ordinary prose is untouched. An unclosed chain terminates at a blank line or the end of its block, so it cannot consume unbounded content.

** Fallback rendering

An unrecognised spell degrades to its target. The parser needs no knowledge of the spell to do this: drop the spell, render the target as it would have rendered without it. Content targets render as content, references render as ordinary references, and a spell with no target simply does nothing.

This is why explicit targeting matters beyond disambiguation. With a target slot, "what survives when this fails" has one answer for every spell, including spells the parser has never heard of.

** Maths (~:math~, ~:$~)

Maths notation is dense with characters Indue also uses (~^~, ~_~, ~*~, ~#~, ~{}~), so it is written as a literal string in a scroll, where none of them fire:

#+begin_example
:math[E = mc^2]
:$[E = mc^2]               ; :$ is an alias for :math
#+end_example

~:$~ is an alias, not a glamour: there is no bare ~$...$~ paired form. Ordinary prose uses ~$~ for currency constantly (~$5~), and a scroll gives maths the explicit visual boundary it wants anyway.

Rendering maths requires a typesetting library, so an application without one is not expected to typeset it. Under parse-don't-fail an unrecognised ~:math~ degrades to its literal content, which stays readable, so the same file works in a task manager and typesets properly in a journal application that implements it.

** No spell is named after a symbol

Spells are named with words. No spell takes a symbol for a name, and the
naming carries no special meaning: a spell called ~:x~ is short, not
structural.

Configuring how a structural marker renders is the one job that might seem
to want a symbol name. It does not: ~:list~ and ~:step~ do that job, and
they say what they configure rather than requiring the reader to know which
character means which (see List and Heading Schema Declarations).

With no category reserving them, symbols are an ordinary naming option, free
for whatever reads best.

That is why ~:>~ can mean "active" without ambiguity. It is not configuring
~>~; it is a short name for a task state, chosen because the glyph reads as
forward motion.

** The void (~[]~)

An empty container is a *void*: a value-shaped absence. It is written ~[]~
and carries no value at all, which is different from carrying an empty
string.

A void is only meaningful where a spell defines a meaning for it. Most
spells have none, and a void handed to one of those is simply an argument
with nothing in it. Where a spell does define one, the meaning is that
spell's own and is documented with it.

The clearest use is in per-depth chains, where a void means *ditto*: keep
following the chain established by the last explicit value (see List and
Heading Schema Declarations).

#+begin_example
:step<[A.] [] [] [i.]>     ; A., then two depths of A.'s own chain, then i.
#+end_example

** Spell forms, summary

| Form                | Meaning                                        |
|---------------------+------------------------------------------------|
| ~:fn~                 | Switch: no inputs, no target, paints its scope |
| ~:fn<a b>~            | Inputs only                                    |
| ~:fn[string]~         | A single unparsed string input                 |
| ~:fn:word~            | Grab rule: the glued word is the target        |
| ~<ref>.fn~            | Construct target, leading                      |
| ~:fn.<ref>~           | Construct target, bonded                       |
| ~[text].fn~           | Construct target, unparsed content             |
| ~{rich}.fn~           | Construct target, rich content                 |
| ~:fn@<ref>~           | Target of that spell alone                     |
| ~:fn:: ... ::fn~      | A shell (see Shells)                           |

* Glamours: Shorthand for Spells

A *glamour* is a single character that stands in for a spell. Glamours are not a second system: every glamour form expands to a spell form, and every rule from the Spells section applies unchanged. They exist because a handful of operations are written constantly, and a one-character form is worth having for exactly those.

| Character | Spell         |
|-----------+---------------|
| ~*~         | ~:bold~         |
| ~/~         | ~:italic~       |
| ~_~         | ~:underline~    |
| ~%~         | ~:strike~       |
| ~`~         | ~:code~         |

Superscript, subscript, and maths have no glamour; they are the ~:sup~, ~:sub~, and ~:math~ spells, the last with ~:$~ as an alias. They are far less frequent than the five above, and a glamour costs a character that then needs escaping in ordinary prose.

** How a glamour expands

Two rules generate every glamour form:

- A *single* glamour is the spell plus its wall: ~*~ is ~:bold:~
- A *pair* of glamours brackets a rich target: the opener is ~:bold.{~ and the closer is ~}:~

Everything else follows from the targeting rules already given.

** Runs collapse

A run of the *same* glamour character means what one means. ~***~ is ~*~, and ~```~ is ~`~.

#+begin_example
***WOW***                  ; bold, the same as *WOW*
#+end_example

This is not a special rule for glamours. A glamour sets a property, and setting a property twice is setting it once: ~:bold.bold~ is ~:bold~, exactly as ~:bg<red>.bg<red>~ is red. Repetition is idempotent everywhere in the language, and glamours are no exception.

The practical effect is that extra marks are available for emphasis without changing meaning. ~***WOW***~ reads as louder than ~*WOW*~ and renders identically.

*** A run is one character repeated

A run stops when the character changes. ~***///word*~ opens with ~***~, which collapses to ~*~; the ~///~ is not part of the opener, because it is a different character.

#+begin_example
***///word*                ; bold, with "///word" as literal text
*[///word]                 ; the same
[///word]*                 ; the same
#+end_example

This is what keeps run-scanning a single rule: consume one character while it repeats, then stop.

*** Single glamour, bare word (the grab rule)

#+begin_example
This is *bold right here
#+end_example

~*~ expands to ~:bold:~, and the grab rule takes the glued word. Only "bold" is bold; the rest of the line is ordinary text. Nothing needs closing, and nothing can run away, because the grab rule terminates at whitespace.

#+begin_example
*word          expands to    :bold:word
#+end_example

*** Single glamour, container target

#+begin_example
*[bold words]              ; a literal target
*{bold with #tags inside}  ; a rich target: inner content is parsed
*<@alice>                  ; a reference target
#+end_example

These expand exactly as the wall form would:

#+begin_example
*[text]        expands to    :bold:[text]
*{text}        expands to    :bold:{text}
*<ref>         expands to    :bold:<ref>
#+end_example

*** Paired glamours

If a matching closer appears on the same line, the glamour spans everything between:

#+begin_example
This has *bold words* in it
#+end_example

#+begin_example
*text*         expands to    :bold.{text}:
#+end_example

The parser scans the current line for a closer. Found one, paired mode. No closer, the grab rule applies instead.

*** Untargeted glamours paint their scope

A glamour with no target behaves like any untargeted spell: it paints from where it sits to the end of its enclosing scope.

#+begin_example
,* This whole block is bold
Plain text * and everything after this in the block is bold.
#+end_example

** Stacking requires a bracket

Different glamour characters may be stacked, which is ordinary bond chaining. Stacking *requires a bracket* immediately after the marks:

#+begin_example
*/[bold and italic]        expands to    :bold.italic:[bold and italic]
_*{underline and bold}     expands to    :underline.bold:{...}
#+end_example

Order within the stack does not matter, because these spells govern different properties.

*** Why the bracket is required

Without it, a mixed sequence would be ambiguous: the parser could not tell where a stack ended and content began, and ~*/word~ could be either bold-and-italic or bold applied to the literal text ~/word~.

Requiring a bracket removes the question. A run is one character repeated, and if the run is followed by a bracket the parser keeps collecting marks; otherwise the run is complete and content begins. One rule, one character of lookahead, nothing to match pairwise.

So ~*/word~ is bold applied to ~/word~, and ~*/[word]~ is bold and italic applied to ~word~.

** Glamours are inline

A glamour is glued to its content. A glamour character alone at the end of a line opens nothing, because there is nothing glued to it.

Regions that cross lines are what shells are for:

#+begin_example
*:: this crosses blocks freely ::*
#+end_example

That is a deliberate division. A glamour that spanned lines would look almost identical to a shell and behave differently at a blank line, and telling them apart by eye would be impossible. Glamours handle words and phrases; shells handle regions.

** Nesting

Glamours do not nest by wrapping. Since a run of any glamour character closes an open span, an inner mark ends the span rather than opening a nested one:

#+begin_example
*_text_*      → bold, ending at the first _
#+end_example

To combine marks, stack them (~*_[text]~). To include a literal mark inside styled content, use the bracket form (~*[/_text/_]~), where the inner characters are content rather than a glamour position.

** Glamours open shells

A glamour run followed by a colon run opens a shell, exactly as a spell chain does. A shell takes *effects*, and a glamour is shorthand for an effect, so nothing special is needed:

#+begin_example
*:: ... ::*                ; the same as :bold:: ... ::bold
*/:: ... ::*               ; bold and italic, stopping bold
#+end_example

This is distinct from the *paired* glamour form, which is bounded: ~*text*~ expands to ~:bold.{text}:~, a conduit that ends where it ends. A region needs the colon run.

** Mid-word glamours

A glamour followed immediately by a bracket is always an opener, whatever precedes it. Ordinary prose does not produce ~*[~, ~*{~, or ~*<~, so this is safe and it is what makes mid-word formatting work:

#+begin_example
abso*[FRICKEN]lutely
#+end_example

The closing bracket ends the scope, and "lutely" resumes as ordinary text. A trailing glamour with no bracket after it, as in "Free*", is untouched: the relaxation only applies when a bracket immediately follows.

To use a glamour character literally elsewhere, escape it with a nick: ~\*minute~ renders as a literal asterisk.

** Changing what a glamour does

A glamour character is never rendered: ~*~ disappears and only the styled text remains. There is therefore no glyph to configure. What you would want to change is what the *spell* does, and that is ordinary targeting:

#+begin_example
<:bold>.weight<600>        ; :bold now means semibold, so * does too
#+end_example

Because a glamour is nothing more than shorthand for its spell, buffing the spell buffs the glamour. No separate configuration mechanism exists or is needed (see No spell is named after a symbol).

** Why the set is small

A glamour costs a character that can then never be ordinary text without escaping. That price is worth paying only for operations written constantly, which is why the set is five rather than open.

Everything rarer uses spell syntax, which is unlimited and needs no glyph budget at all. Superscript and subscript are ~:sup~ and ~:sub~. Maths is ~:math~, with ~:$~ as an alias rather than a glamour: ~$~ stays ordinary text, so prices and variables need no escaping, and only ~:$~ means anything.

* Goety

*Goety* is Indue's borrowed magic: a small closed set of fixed shapes taken from common markup convention, recognised whole, that produce Indue constructs without going through the spell system.

Goety exists for one reason, familiarity. People arriving from other markup already know these shapes, and there is no reason to make them relearn a gesture they already have.

** Goety is not glamour

Glamours and goety are both short, but they are not the same kind of thing, and the difference matters.

A *glamour* derives from the system. ~*word~ has a defined expansion into ordinary spell grammar, inherits every targeting rule unchanged, stacks by bond-chaining, and is configured by targeting the spell it stands for. It is the spell system wearing one character instead of five, so when you need more, you write the longer form of the same thing.

*Goety* derives from nothing. It has no expansion you could work out from the grammar, it does not compose, it cannot be extended or configured, and its parts carry no independent meaning. It is a lookup-table entry that happens to produce a valid construct.

That is why the set is closed and why it may break conventions the rest of the language keeps. Goety is a compatibility layer, not a demonstration of how Indue works, and nothing should be inferred from its shapes.

** The recognised set

| Goety           | Equivalent          | Notes                        |
|-----------------+---------------------+------------------------------|
| ~[label](url)~    | ~:link[url]:label~    | Markdown-style link          |
| ~[]~ / ~[ ]~        | ~:task<open>~         | Open task, block start only  |
| ~[>]~             | ~:task<active>~       | Active task, block start only |
| ~[x]~             | ~:task<closed>~       | Closed task, block start only |

#+begin_example
See [the docs](https://example.com) for details.

[] Buy groceries
- [>] Read foundational papers
+ = [x] Ship the beta
#+end_example

The checkbox forms are recognised only at the start of a material block, after any socket and its space. They are not welded to list items: a heading or a paragraph can carry one, because structure and task semantics are independent (see The Task Model).

** Why they do not follow the container rules

In ~[label](url)~ the scroll holds rendered text and the vessel holds data, the reverse of Indue's convention. This is not an inconsistency to resolve: the shape is not parsed as a scroll followed by a vessel at all. It is matched as one fixed pattern and never decomposed, so its parts carry no independent meaning.

Outside a spell, adjacent containers have no meaning of their own, so recognising these shapes creates no ambiguity with ordinary syntax.

The checkbox forms sit in a position where a scroll would otherwise embed its contents. They are matched first, as whole patterns, which is what lets ~[]~ mean an open task at block start and an empty scroll everywhere else.

** Goety may be generous where the core is strict

Because goety is a compatibility surface rather than a design statement, it can absorb conventions that are popular but semantically muddier than Indue's own vocabulary.

~[!]~ for a blocked task is the likely example. The core deliberately has no blocked state, because blocked composes with every lifecycle position and belongs in a tag (see The Task Model). A goety form may still be provided for people who expect it, with the caveat stated where it appears: ~[!]~ occupies the state slot, while ~[x] #blocked~ and ~[>] #blocked~ say more.

** When to prefer the spell form

The spell form is more capable and should be preferred whenever anything beyond the plain case is needed: a chained effect, a reference target, a styled label, a link to a station rather than a URL.

#+begin_example
[label](url)                       ; plain case, fine
:link[url]:label                   ; the same thing, idiomatic
:link[url].bold:label              ; chained, only the spell form can do this
:link@<^section>                   ; link to a block by station
#+end_example

Goety is also the least self-describing part of the language. ~:link[url]:label~ can be understood by someone who has never seen Indue, because its parts say what they are; ~[label](url)~ can only be recognised, not worked out. Where a document is meant to survive without the program that wrote it, the spell form is the one that carries its own meaning.

* The Task Model

Task management is one of the two reasons Indue exists, and it is the reason the language reaches past formatting into semantics at all. A task's *lifecycle state* is therefore not vocabulary catalogued alongside other spells: it is a guarantee this specification makes, so that a task written in one application means the same thing in every other.

** Three states, fixed

~:task~ takes exactly one of three values. The set is closed. There is no fourth idiomatic state, and applications must not add one.

| Value    | Meaning                                                          |
|----------+------------------------------------------------------------------|
| ~open~     | Nothing has happened. No concrete effort has begun and nothing has been done to mark that it has. |
| ~active~   | Something has started. The task is under consideration or in hand, and the intent is to continue. |
| ~closed~   | The task is no longer being worked on and there are no plans to resume. |

~closed~ is deliberately neutral about outcome. A task that was finished and a task that was abandoned occupy the same lifecycle position: both have left the working set. *Why* it closed is a separate question, and one for tags.

*** Why exactly three

These three are the distinctions that cannot be expressed any other way. Everything else a task-management system usually offers is either a *reason* (why is this not moving) or a *qualifier* (what kind of closed), and both of those compose with a lifecycle position rather than replacing it.

Blocked is the clearest case. A task can be blocked and open, blocked and active, or blocked and closed, and all three say something true and distinct. A single state slot cannot express any of them, because occupying the slot with ~blocked~ throws away where the task actually sits. As a tag it composes:

#+begin_example
- :o Draft the migration plan #blocked
- :> Rewrite the parser #blocked #waiting-on-review
- :x Ship the beta #blocked
#+end_example

The same holds for waiting, deferred, in-review, cancelled, and superseded. Tags carry them, and carry more of them at once than a state ever could.

*** Why they are fixed rather than default

An open vocabulary would erode the guarantee. If ~:task<deferred>~ were merely unrecognised rather than invalid, then a document's task semantics would depend on which spell packs the reader happened to have, and cross-application filtering would silently miss tasks.

Three fixed values mean any application can answer "show me everything active" correctly for any document, including documents using a vocabulary it has never seen (see Custom states, below).

** Writing a task

Each state has three forms: the full spell, a short alias, and a borrowed shape.

| State  | Spell           | Alias | Goety |
|--------+-----------------+-------+-------|
| open   | ~:task<open>~     | ~:o~    | ~[]~    |
| active | ~:task<active>~   | ~:>~    | ~[>]~   |
| closed | ~:task<closed>~   | ~:x~    | ~[x]~   |

#+begin_example
- :o Buy groceries
- :> Read foundational papers
- :x Fix the sink
#+end_example

~:o~ and ~:x~ are ordinary spell definitions, not built-in syntax:

#+begin_example
<:o>.task<open>:
<:x>.task<closed>:
#+end_example

They are shipped with an application rather than hardcoded in a parser, which is why they can be read and understood from inside the language. They may not be redefined: the three values are a guarantee, and a document that redefined ~:x~ would break it.

~:>~ is different, and is built in rather than defined. A vessel closes on its first ~>~, so a spell whose *name* is ~>~ cannot be written as a target: ~<:>>~ would close after ~<:>~ and leave a stray bracket. The name is reachable when *invoked* (~:>~ is unambiguous, since nothing is waiting to close) but not when *referenced*, which is exactly what a definition requires.

This is a real limitation rather than an oversight, and it is worth stating plainly: *a spell named with ~>~ can be used but not defined, targeted, or referenced.* ~:>~ is therefore reserved and built in, and no user-defined spell may take a name containing ~>~. Custom active states use ordinary names (~:doing~, ~:wip~), which have none of these problems.

*** The goety forms

~[]~, ~[>]~, and ~[x]~ are goety (see Goety), recognised only at the start of a material block, after any socket and its space:

#+begin_example
[] Buy groceries
- [>] Read foundational papers
+ = [x] Ship the beta
#+end_example

~[ ]~ is accepted as a synonym for ~[]~, since writers arriving from other markup will type it. ~[]~ is the documented form: it is one character shorter, more visually distinct from ~[x]~, and needs no cursor work to replace its contents.

Unlike other markup, the checkbox is not welded to a list item. It works at the start of *any* block, so a heading or a paragraph can be a task, and the socket, if there is one, is a separate concern. Structure and task semantics stay independent, as they do everywhere else in the language.

The goety forms map to the three values directly, not through the aliases. Their meaning does not depend on any definition being present.

** Block tasks and span tasks

A task spell that targets a *block* sets a block property, so it shadows: a block has one task state, and it is whatever the last block-targeting task spell said. A task spell that targets a *span* is a task in its own right, and these accumulate: a block may carry several.

#+begin_example
- :o Buy groceries
#+end_example

One block task, no span tasks.

#+begin_example
- When you get home, [feed the cats].o and [let out the dogs].o :on<2026-08-15> :repeat[daily]
#+end_example

Two span tasks on one block, with one schedule between them. Without span tasks this would need two blocks and a duplicated schedule.

*** Containment, not parenthood

Span tasks are *contained by* their block. They are not its children in the sense that matters for state: *a block's task state depends only on the last block-targeting task spell*, never on the spans inside it.

That is deliberate. A rollup sounds helpful until a span task is optional, added later, or someone else's, at which point a schedule would be held hostage by something the author never meant as a gate. Closing the block task is the author's judgement that the line is done.

Applications may of course *display* span tasks nested under their block. The word to avoid is the one that implies derived state, since Indue already uses parent and child for genuine ownership through nesting.

*** Querying

A query for tasks returns *each task*, not each block. A block with two open span tasks and an open block task yields three results.

Each result renders as one line: the text of the span for a span task, or the whole block's text, flattened, for a block task. An agenda list therefore has one uniform shape regardless of what matched, an action control and a line of text, with no nesting to render.

** Custom states

A document may define its own vocabulary. A custom state is an ordinary spell definition that declares which of the three lifecycle positions it occupies:

#+begin_example
<:todo>.task<open>:
<:doing>.task<active>:
<:review>.task<active>:
<:shipped>.task<closed>:
<:dropped>.task<closed>:
#+end_example

~.task<state>~ is mandatory. It is what keeps custom vocabulary portable: an application that has never heard of ~:review~ still knows the task is active, so filtering, sorting, and agenda views work on documents written in a vocabulary the application does not know.

Custom states are first-class. They style like any spell, they can carry their own presentation, and they are invoked the same way:

#+begin_example
<:review>
.task<active>
.span-bg<#f5e6a3>
.embed[REVIEW]:
#+end_example

*** Cycles

A *cycle* is a named, ordered list of states. It is what an application advances through when a reader toggles a task.

#+begin_example
:cycle[gtd]<:todo :doing :waiting :shipped>
:cycle[bugs]<:todo :doing :review :shipped :dropped>
#+end_example

The name is a scroll, an opaque label for display. The ordered states are a vessel of referenced spell names.

Cycles are declared rather than inferred. A state could in principle name its own successor, and cycling would emerge from following those links, but an application would then have to walk the whole graph to know what options exist, and could not tell which cycle a shared state belonged to. A declared list gives an application the display name, the full ordered set, and unambiguous membership without any graph walking.

If a state appears in more than one cycle, the last cycle declared wins for that state. If two cycles are declared under the same name, the later replaces the earlier. Both follow the ordinary cascade; neither is checked or warned about. A document that makes its own cycling ambiguous is a document problem, not a language one.

** Recommendations for applications

Task semantics are only portable if applications treat them consistently. Implementations should:

- *Filter by lifecycle state.* Offer open, active, and closed as filters, and resolve custom states through their declared ~.task~ value so documents using unknown vocabulary still filter correctly.
- *Filter by tag alongside state.* Because reasons and qualifiers live in tags, useful views are combinations: active and ~#blocked~, closed and ~#dropped~, open and not ~#someday~.
- *Surface the cycles a document declares*, by name, and let the reader choose which one a toggle advances. Do not assume a single cycle.
- *Fall back to the three states* when no cycle is declared, advancing open → active → closed.

Interaction design is not specified. Tap to toggle, hold to advance, keyboard cycling, and drag-between-columns are all reasonable, and are the application's to choose. What must be consistent is the *meaning* of the states, not the gesture that changes them.

* The Scheduling Model

Scheduling is the second reason Indue exists, and like the task model it is specified here rather than catalogued, because it is a guarantee: two applications must resolve the same document to the same dates, or a shared vault means nothing.

The catalogue of scheduling spells, and the full recurrence grammar, are in *The Indue Spellbook*. What belongs here is the shape of the model and the guarantees it makes.

** One axis per spell

Scheduling is carried by five separate concerns, and no spell carries two of them.

| Axis          | Carries                          |
|---------------+----------------------------------|
| Date          | The anchor: which day            |
| Time of day   | Clock times within that day      |
| Repetition    | The pattern                      |
| Series bounds | Where a repeating series runs    |
| Exceptions    | Occurrences to omit              |
| Completion    | When occurrences were finished   |

#+begin_example
- :o Team standup :on<2026-04-07>.start<09:00>.end<09:15> :repeat[weekdays] :until<2026-12-31>
#+end_example

Keeping time of day separate from date is what avoids composite date-time formats, and it gives duration for free: a start and an end are two clock times, not a special range type. Keeping *series* bounds separate from *clock* times is why they have their own names, ~:from~ and ~:until~, rather than overloading start and end.

** The pattern is a closed grammar, not natural language

A recurrence pattern is written as a readable string:

#+begin_example
:repeat[every 2 years on 3rd wednesday of march]
#+end_example

It looks like English, and that is deliberate: a scheduling rule should be legible to someone opening the file with no application, which ~FREQ=YEARLY;INTERVAL=2;BYMONTH=3;BYDAY=3WE~ is not.

But it is *not* natural language parsing. The grammar is closed: three clauses in a fixed order, each introduced by its own keyword, with closed vocabularies for periods, ordinals, days, and months. There is exactly one reading of any valid pattern, and phrasings outside the grammar are not accepted rather than being guessed at.

This distinction matters for portability. An open natural-language parser would mean two applications could legitimately disagree about what a string means, which is precisely what a shared vault cannot tolerate.

** The pattern says how often, never when

A pattern carries no date. The anchor comes from the date spell on the same item, and where the two appear to disagree, the pattern wins and the anchor supplies only a starting point.

#+begin_example
- :o Book club :on<2026-04-20> :repeat[every month on 3rd saturday]
#+end_example

That produces third Saturdays. The anchor says when to begin looking, not which day of the month to use.

** One schedule per block

Scheduling spells set *block properties*, so each shadows: a block has one due date, one pattern, one set of bounds. Writing two means the later wins, exactly as with any property.

This is a real constraint rather than an accident of the fold, and it is worth stating: *a block may carry many tasks, but only one schedule.* Span tasks accumulate; scheduling does not. A block with several tasks recurs once, on one pattern, and advances when its block task closes.

Because position is semantically irrelevant under shadowing, scheduling is idiomatically written at the *end* of a block, where it does not interrupt the reading of the content it describes. This is the same reasoning that puts configuration in a footer satchel.

** Completion state

~.after<completion>~ needs to know when the task was last completed, and that is the one piece of scheduling a document cannot supply by authoring alone: it is written back by an application.

~:completions~ carries it, either on the task's own line or on the line immediately below:

#+begin_example
- :o Water plants :on<2026-04-07> :repeat[weekly].after<completion>
:completions[2026-04-07 2026-04-14 2026-04-21]
#+end_example

The second line is an astral block: it has no material content, so it renders nothing. The dates are visible to anyone reading the file directly and absent from the rendered document.

*** Why adjacency rather than a name

~:completions~ binds to the block it sits on, or to the block immediately above it. It could instead have named its task through a station, which would survive reordering, but that would tax the writer with supplying a handle for something they never asked for. Adjacency sets it up for free.

A second ~:completions~ below the first does not compete: it binds to the astral block above it, which has no task and no completion state, so it is inert. There is nothing to search for and nothing to disambiguate.

Content inserted between a task and its completions detaches them, and the schedule stops advancing. This is deliberate: the failure is visible rather than silent. An application that maintains the log should keep the two together, and may reattach or regenerate a detached one.

*** Authored and maintained state

~:completions~ is the first construct in the language whose values an *application* writes rather than a person. That is worth knowing for tooling: a diff on a document may show completion dates changing without an author having edited anything, and a merge of two copies should union the dates rather than take one side.

Everything else in Indue is authored. Where an application writes, it should write only here.

** Authoring format, not interchange format

Every pattern maps to exactly one RRULE, so export to calendar systems is deterministic. Import is not: shorthands expand, and a pattern anchored to a completion date has no iCalendar equivalent at all, since iCalendar describes calendars rather than tasks.

Indue is where a schedule is written and read; RRULE is how it travels. Applications that export to calendar systems should perform the conversion, and should not treat RRULE as a storage format to round-trip through.

* Shells: Region Effects

A shell applies effects over an open-ended *region* rather than a bounded container. It is the primitive for effects that span content, and for effects that overlap.

A shell is opened by a spell chain or a glamour run ending in a *colon run*, and closed by a matching run:

#+begin_example
:span-bg<red>:: ... region ... ::span-bg
:quote:: multi-paragraph quote ::quote
*:: ... region ... ::*
#+end_example

** What a shell holds

A shell holds *effects in force*, not a single spell. Several bonded before one colon run all take effect over the region:

#+begin_example
:bold.italic.span-bg<yellow>::
Everything here is bold, italic, and highlighted.
::
#+end_example

That matters for closing, which operates on individual effects rather than on the shell as a whole.

** Glamours open shells

A glamour run may open a shell, since a glamour is shorthand for a spell and a shell takes effects rather than names:

#+begin_example
*::                        ; the same as :bold::
*/::                       ; the same as :bold.italic::
::*                        ; stops bold
#+end_example

The run collapses as it does anywhere else, so ~***::~ and ~*::~ are the same.

Symbol spells work the same way. ~:>~ is a spell name rather than a glamour, so it opens and closes like any other:

#+begin_example
:>:: ... region ... ::>
#+end_example

** Spanning

A shell spans arbitrary blocks, running from its open until it is closed, crossing paragraphs, lists, and other structure freely. This is what makes shells, rather than bounded containers, the way to apply an effect to a whole section.

A shell opened at a socket's block-start position auto-closes when structure outdents to or past that socket's depth: its subtree has ended. This lets an effect span exactly one item's subtree with no closer to write.

Any shell still open at end-of-document auto-closes there.

** Closing

Three things decide what a closer does: its *length*, whether anything is *glued* to it, and what that glued thing names.

*** Length must match

A closer only closes shells opened with a run of the same length. ~::~ closes ~::~ shells; ~:::~ closes ~:::~ shells and leaves ~::~ shells untouched.

This is what makes hypershells content-safe (see below). It also means the colon count is part of a shell's identity, not decoration.

*** A bare closer closes everything

A colon run with nothing glued to it closes *all* open shells of that length:

#+begin_example
:bold::
:span-bg<red>::
:italic::
Some text with three shells in force.
::                         ; all three close
#+end_example

This is the fast reset: end everything, return to plain text. It is deliberately blunt, and it is why the precise form exists.

*** A glued closer stops one effect

A closer with a name glued to it stops *that effect only*, in the innermost shell where it is active. Other effects in the same shell continue:

#+begin_example
:bold.italic::
Both bold and italic here.
::bold                     ; bold stops, italic continues
Still italic.
::italic                   ; italic stops; the shell has nothing left, so it closes
#+end_example

A shell closes when it has no active effects remaining. Closing a shell is therefore something that *happens*, rather than something you do directly.

Where the same effect is active in more than one open shell, a glued closer stops the innermost. This matches how nesting resolves everywhere else.

*** Closers that match nothing are inert

A closer naming an effect that is not in force, or a length that no open shell used, does nothing. Recover forward.

*** The colon forms never collide

~:name::~ has the run *after* a spell and opens. ~::name~ has the run *before* a name and closes that effect. ~::~ alone closes everything of its length. Position and attachment disambiguate them locally, with no lookahead.

** Overlap

Because closes name effects, shells may overlap without nesting, which containers cannot express:

#+begin_example
:bold:: ... :italic:: ... ::bold ... ::italic
#+end_example

Bold stops while italic is still in force.

At render, an overlap splits into consecutively-nested style zones: a new zone begins at each open or close, and its applied effects are the set in force over that span. When an effect stops mid-region, inner tags close, that effect drops, and the survivors reopen in *original open order*, so specificity stays stable. Within a zone, a property set by two shells resolves inner-wins, the same stack order as nesting.

This split is a pure function of the shell stack, so every renderer produces the same zones.

** Hypershells

A colon run of *three or more* opens a *hypershell*: a shell whose delimiter is length-matched, so its content cannot defeat it.

#+begin_example
:code:::
std::cout << Foo::Bar;
::allocator<T>
:::
#+end_example

Nothing in that content closes the region, because a two-colon run does not match a three-colon shell.

*** Why they are needed

Shells are safe for content Indue parses, and unsafe for content it does not. ~::~ is common in code: C++ and Rust paths, PHP static calls, Ruby constants. A bare ~::~ inside a code region would fire the close-everything rule, silently ending every open shell in the document from wherever the code happened to contain it.

Length-matching removes the problem rather than working around it. Content containing ~:::~ is held by a four-colon shell, and so on upward. There is no content that defeats a hypershell, because the delimiter can always be lengthened past it.

*** Closers stand alone

A hypershell's closer must be *alone on its own line*. A line with anything else on it is content, whatever colons it contains:

#+begin_example
:code:::
let x = some_long_module
    ::nested
    ::function();
:::
#+end_example

The indented ~::nested~ is content, because the line does not consist solely of a colon run.

This makes a hypershell a block construct. There is no inline form: inline code uses ~`x`~ or ~:code[x]~, where content short enough to sit in a sentence rarely fights the delimiter.

*** What they keep and what they cost

Hypershells keep named closing, so ~:::bold~ stops one effect in a three-colon shell exactly as ~::bold~ does in a two-colon one.

What they cost is the *compact* close-everything: since a closer must be alone on its line, closing several hypershells means several lines. That is the trade for content safety, and it lands on the construct where safety matters most.

** Choosing a form

| Want                                    | Use                    |
|-----------------------------------------+------------------------|
| A region over parsed content            | ~::~ shell               |
| A region over content Indue must not read | ~:::~ hypershell       |
| A bounded span, not a region            | A container target     |
| One word                                | A glamour or the grab rule |

* Sigils: Tags

Sigils (tags) use ~#~, the universal tagging character:

#+begin_example
- Buy groceries #errand #personal
- Read about #[machine learning] approaches
#+end_example

- Single-word sigil: ~#errand~
- Multi-word sigil: ~#[machine learning]~ (closing ~#~ needed only for multi-word sigils)
- Whole-line sigil: ~#~ at line start sigils the entire line

A sigil marks a tag or category. Semantically, it identifies the block it appears within as belonging to that category, much like a Markdown hashtag. A block tagged ~#meeting~ is "about" meetings; a list item tagged ~#errand~ is an errand.

Sigils and signets share a single entity namespace (a codex defined for ~alice~ covers ~#alice~, ~@alice~, and ~^alice~ identically). The sigil form (~#~ vs. ~@~ vs. ~^~) communicates *intent* (tag vs. mention vs. anchor), not behavior. The spell's nature decides block or span (~#~/~@~/~^~ style their rendered expression). See the role matrix in Stations.

* Signets: Entity References

Signets (entity references) use ~@~:

#+begin_example
@alice mentioned this in the meeting.
See @intro for background.
#+end_example

Signets can refer to people, documents, stations, or any named object in the system. Like sigils, they may or may not resolve to a specific target. A signet without a matching station is still valid and carries meaning.

Sigils and signets share an entity namespace; a codex on ~alice~ covers all forms. The sigil form (~#~ vs. ~@~ vs. ~^~) communicates intent (tag vs. mention vs. anchor). Styling follows rendering: multiple signets on a line each style their own rendered mention, leaving the block neutral. See the role matrix in Stations.

* Stations: Named Places

A station marks a place in a document so it can be navigated to, referred to, and configured. It comes in two forms that differ only in whether the anchor itself renders.

** Stations (~^name~)

A ~^~ glued to a name anchors a *span*. A block may hold many, one per span you want to anchor:

#+begin_example
- = Introduction ^intro
See @intro for background.
#+end_example

A station is an *entry and an endpoint*: you can navigate from it and arrive at it. That bidirectionality is why chaining stations forms a trail (below). Styling a visible station styles its rendered span. Its name participates in the shared namespace and can carry a codex.

A ~^~ glued to a name is a station; a ~^~ with surrounding space is literal.

** A station names a place, not a tier

A station resolves to *a place in the document*. It does not decide whether an effect lands on the text there or on the block containing it, the *spell* decides that, because every spell has a fixed nature (see Span and block natures in the Spellbook).

#+begin_example
:bold@<^intro>             ; :bold is span-natural, so the anchored text goes bold
:card@<^intro>             ; :card is block-natural, so that block becomes a card
#+end_example

Both target the same station. Neither is ambiguous, because neither spell has two possible readings to choose between. This is why Indue needs no separate block-handle construct: one reference kind is enough when nature lives on the spell.

*** Stations are always visible

A station renders its anchor. There is no hidden form, because an invisible named handle is what a *source* is (see Sources). The two divide cleanly: a station is a visible place you go to, a source is an unrendered name you look things up by.

A block may carry both, and often will:

#+begin_example
^alice Alice Chen
&alice&
:info[role | Engineer]
#+end_example

*** Multiple stations on one block

A block may carry more than one station. They are *aliases* resolving to one identity; effects addressed through any alias accumulate and resolve under the standard last-write-wins cascade.

Machine-generated identifiers are not stations. An application needing to address a block writes a *source*, which renders nothing and therefore does not clutter the text (see Sources).

*** Closing the anchor (~^name^~)

A station may optionally be closed with a trailing ~^~, which bounds the anchored span explicitly rather than letting it run to the end of the word. Multi-word names use a scroll, exactly as sigils do:

#+begin_example
^intro^                    ; explicitly bounded
^[my long name]            ; multi-word, parallel to #[multi word]
#+end_example

** Shared namespace and role matrix

~#~ (sigil), ~@~ (signet), ~^~ (station), ~&~ (source), and bare names all resolve into *one shared namespace*, so they find each other.

They share resolution but differ in *role*:

| Form   | Departs? | Arrives? | Styling affects                |
|--------+----------+----------+--------------------------------|
| ~#~      | yes      | no       | the rendered tag               |
| ~@~      | yes      | no       | the rendered mention           |
| ~^name~  | yes      | yes      | span or block, by spell nature |
| ~&name&~ | no       | yes      | nothing; it is not rendered    |

- ~#~ and ~@~ are *entry only*. They render specially and are clickable, and where a name has no endpoint they navigate nowhere.
- ~^name~ is *entry and endpoint*, which is what makes trails possible.
- ~&name&~ is *endpoint only*, and it is the one endpoint that does not render. See Sources.

A *bare name* is the entity union selector, matching every rendered form (~#~, ~@~, ~^~) of that name. It is meaningful in selector and target position, not in free prose (a bare word in prose is just a word).

* Sources: Canonical Records

A *source* is the one place a name's facts live. It is written ~&name&~, and unlike every other entity it does not accumulate references: repeated declarations *shadow*, so a name has exactly one source, and following a mention of that name has exactly one destination.

#+begin_example
&alice&
:info[
role   | Engineer
team   | Platform
email  | alice@example.com
]
#+end_example

** Not rendered

A source names a block without rendering anything itself. The block may hold visible content, and often should, but the name is a handle rather than a mark.

That makes a source the natural home for a machine-generated block identifier. An application needing to address a block writes a source with a generated name, and nothing appears in the document:

#+begin_example
&n3b7c2&
#+end_example

Human names and machine handles are the same construct. One is typed, the other generated, and both resolve identically.

** Properties accumulate, keys become history

Declaring a name twice does not discard the first. *Linking* goes to the last, but *properties* accumulate across every declaration in document order.

Where a key appears more than once, the values form a history rather than overwriting. Reading a property returns the latest; the earlier values remain reachable.

#+begin_example
&goblin|1&
:info[
hp    | 12
mood  | hostile
]

... the fight happens ...

&goblin|2&
:info[
hp    | 4
mood  | fleeing
]
#+end_example

~hp~ now has a history of two values, and a read returns 4. This is what lets a document track an entity's state as it changes, rather than only its final state.

*** Versions

The value after a pipe is the *version*, and it is authored rather than derived from position. It is shorthand for a ~version~ property, so these are the same:

#+begin_example
&goblin|2&
&goblin&
:info[version | 2]
#+end_example

Numbers are the obvious choice because they order, but any value works, and a date is often more useful for a journal.

A version is a stable handle. Inserting another declaration renumbers nothing, because nothing was ever numbered by position.

*** Keep the whole record on the last source

Accumulation is a power feature, and it depends on the reader's application implementing it. A simple renderer that follows a mention shows *that block's* properties, not a merge of every declaration.

So unless there is a reason to track milestones, *put every property on the last source*, even where earlier ones repeat them. The destination is then complete in any implementation, and accumulation adds history rather than being required for correctness.

** How the three marks resolve

Sigils, signets, and stations share one namespace, and a source joins it. Each mark lands where its own meaning points:

| Mark      | Means      | Goes to                            |
|-----------+------------+------------------------------------|
| ~#name~     | categorise | the station: the named place       |
| ~@name~     | mention    | the source: the canonical record   |
| ~^name~     | anchor     | that marked spot, and its trail    |

None of these is a fallback for another. A mention goes to the record because that is what mentioning a thing and following it means: you wanted to know about it. A tag goes to the place because a category is somewhere you gather things.

A ~|value~ after any mark reaches a specific one, which is how a duplicate is disambiguated after the fact:

#+begin_example
@goblin|1                  ; the first source, not the latest
#argument|2                ; the second station on that trail
#+end_example

*** One name is one thing

Sharing a namespace is deliberate. In a personal knowledge base, the same name almost always means the same thing: if you tag ~#project-alpha~ and mention ~@project-alpha~, they are the same project, and you would have noticed when you typed the second one if they were not.

Separate namespaces would put the work in the wrong place. Linking a tag to its record would need declaring, which is effort spent on the common case to serve a rare one. Shared by default puts the ceremony on the exception: if you genuinely need two unrelated things called ~alpha~, name them differently.

It is also what lets the marks compose. A tag reaching a station that lists mentions pointing at blocks works because all of them mean the same name.

** Stations and sources

The two are the same shape, a named place you can reach, and they differ in three ways that follow from what each is for.

| | Station ~^~ | Source ~&~ |
|---+---------+--------|
| Duplicates | cycle, forming a trail | accumulate into one record |
| Rendering | visible | not rendered |
| For | going | knowing |

A station is where you *go*: it marks a span, it renders, and repeating it gives you a route. A source is where you *find out*: it names a block, it renders nothing itself, and repeating it builds a record.

Neither errors on accidental duplication. Repeat a station and you get a trail you did not ask for but can use; repeat a source and you get merged properties with the latest winning. Both degrade into something sensible, which is what lets them be power features without being hazards.

A block may be both:

#+begin_example
^alice Alice Chen
&alice&
:info[role | Engineer]
#+end_example

Here ~^alice~ marks the name visibly, ~&alice~ makes that block the canonical record, and both resolve to the same place from their own marks.

** Backlinks are derived, not stored

Every occurrence of ~#alice~ is discoverable by reading the document, so a list of them is *derivable*. An application builds it by scanning; nothing needs writing down, and nothing can go stale.

Facts that cannot be derived are the ones that belong in a source. An identifier, an email, a curated list of links: these exist only because someone wrote them, and if they are not in the document they are not portable.

That is the test for what a source should hold: *could an application compute this from the text?* If yes, let it. If no, write it down.

*** Applications may keep their own index

An application is free to maintain its own entity index rather than using sources, and doing so does not affect document validity. The text still parses, the marks still resolve, and another application reading the same file sees the same content.

What is lost is portability of the derived data. Records held in an application's database rather than in the document are unavailable to anything else reading the vault. That may be a reasonable trade for a hosted service; it should be a decision rather than an oversight.

*** Queries resolve against the whole Lair

A query's result is defined as if the entire Lair had been parsed, whatever an application actually does to compute it. Incremental parsing, indexes, and caches are all permitted; returning a different answer than a full parse would is not.

That is what makes the query language part of the format rather than part of one program, and it is why the reference implementation can be used to check another. See *Indue Query Syntax*.

*** Resolution must not require an index

Following ~@name~ must not depend on an application having built an index. It is a scan for the last ~&name&~, which a rendering-only application can do.

This is what keeps the format implementable at the small end: a simple application can produce a working wiki, with linking and records, before it has any query engine at all. Backlinks, ranking, and graph views are enhancements layered on top, never prerequisites for the base navigation.

* Comments: Whispers

A *whisper* is a comment, text that lives in the source but never reaches the render. Whispers use the semicolon ~;~. Everything from the semicolon to the end of the line is a comment and is stripped before the body is parsed.

#+begin_example
- Buy groceries          ; trailing whisper, ignored on render
; this whole line is a whisper
:bold:word               ; whispers are fine after spells too
#+end_example

** Graduated levels (Lisp-style)

Like the rest of Indue, the meaning scales with the count of the marker. This mirrors the convention in Lisp dialects, where the number of leading semicolons signals a comment's structural altitude. The character does exactly one thing, comments out the rest of the line, but the count is a readable signal of intent, the same way ~=~ / ~==~ / ~===~ count for heading depth and ~-~ / ~--~ / ~---~ count for list depth.

| Marker  | Convention      | Typical use                                  |
|---------+-----------------+----------------------------------------------|
| ~;~       | Inline whisper  | Trailing note on a line of content          |
| ~;;~      | Block whisper   | Standalone note describing the lines below  |
| ~;;;~     | Section whisper | Heading-level note for a region of the file |
| ~;;;;~    | File whisper     | Top-of-file banner, license, or metadata    |

#+begin_example
;;;; project-config.indue
;;;; vault-wide entity definitions, edit with care

;;; People
;; canonical contacts, names must match the directory
<alice> .color<#4a90d9>.chip :   ; brand blue
<bob>   .color<#d97757>.chip :   ; warm orange

;;; Projects
<project> .bg<#f0f0f0>.card :
#+end_example

The graduated levels are a *convention*, not a parser rule. To the tokenizer, ~;~, ~;;~, ~;;;~, and ~;;;;~ are identical: each comments out the remainder of the line. Tools (formatters, folders, outline views) may treat the higher levels as structural markers, aligning block whispers to the indentation of the code beneath them or surfacing section whispers in a navigation pane, exactly as Lisp editors do. The single character keeps the rule trivial; the repetition is free expressivity for the writer.

** Scope and literal contexts

A whisper is recognized in body text and inside conduits ~{}~ (rich, parsed content). It is *not* recognized inside scrolls ~[]~, which are literal, a semicolon inside a scroll is a literal semicolon, never a comment. This matters for content like code, URLs, and raw data:

#+begin_example
:code<rust>[let x = 5; ; the ; inside the scroll is literal Rust]
:link[https://example.com/path;param]:{label} ; only THIS ; is a whisper
#+end_example

In the first line the semicolon belonging to the Rust statement survives because it sits inside a scroll; the trailing whisper after the closing bracket is stripped. In the second, the matrix-parameter semicolon inside the URL scroll is preserved while the trailing whisper is removed.

** Escaping a literal semicolon

Outside a scroll, use the nick (~\~) to write a literal semicolon that should not start a comment:

#+begin_example
The ratio is 3\;1 in plain prose.   ; renders "3;1", then a real whisper
#+end_example

** Whispers and parse-don't-fail

Whispers are removed in a lexical pass before the socket, glamour, and entity layers run. There is no such thing as an unterminated whisper, the end of the line always closes it, so the no-errors philosophy is preserved trivially. A whisper never spans lines; multi-line notes are simply multiple whisper lines.

* List Nesting: Two Modes

Indue supports two modes for list nesting. Both produce the same AST. The writer chooses whichever suits their context.

** Indented mode

Nesting is determined by physical indentation (tabs or spaces). The parser normalizes both to indent levels. Tabs are recommended for proportional fonts because they render at a visible width.

#+begin_example
- Level 1 item
  - Level 2 item
    - Level 3 item
      Content belongs to Level 3
  + Level 2 ordered item
- Another Level 1 item
#+end_example

Ownership rule: any line indented strictly deeper than a socket belongs to that socket. The exact number of spaces does not matter as long as it is deeper than the parent (Option C).

** Dash-mode

Nesting is determined by repeating the dash character. The final character in the sequence determines the list type.

#+begin_example
- Level 1 unordered
-- Level 2 unordered
--- Level 3 unordered
-+ Level 2 ordered
--+ Level 3 ordered
#+end_example

Dash-mode rules:

- Count of leading dashes determines depth.
- Final character determines type: ~-~ for unordered, ~+~ for ordered.
- Non-socket lines (no leading dashes) belong to the most recent socket above them. Period.
- Leading whitespace on content lines is cosmetic and stripped by the parser.
- A blank line ends the list.
- Trailing child content is not supported. To return to a parent level, create a new socket with fewer dashes.
- Empty sockets are real empty items, not invisible or magic.

The same content in both modes:

#+begin_example
Indented:                    Dash-mode:
- Project Alpha              - Project Alpha
  - Goals                    -- Goals
    - Item A                 --- Item A
    - Item B                 --- Item B
  + Timeline                 -+ Timeline
    + Q1                     --+ Q1
    + Q2                     --+ Q2
- Project Beta               - Project Beta
#+end_example

** Mixing modes

Within a single list, one mode must be used consistently. Dash-mode and indented mode cannot be mixed at the same nesting level. Different lists in the same document may use different modes.

* Heading Promotion

Any list item in either mode can be promoted to a heading by appending ~= ~ (equals space) after the socket characters. The ~=~ is separated from the socket by a space.

#+begin_example
Indented:                    Dash-mode:
- = Project Alpha            - = Project Alpha
  - = Goals                  -- = Goals
    - Item A                 --- Item A
    - Item B                 --- Item B
  + = Timeline               -+ = Timeline
    + Q1                     --+ Q1
    + Q2                     --+ Q2
- = Project Beta             - = Project Beta
#+end_example

** What heading promotion does

A heading-promoted item:

- Appears in the table of contents / outline.
- Receives an auto-calculated heading level (see below).
- Can be navigated to via the heading outline.
- Is otherwise a normal list item, it follows list ownership rules.

A non-promoted item:

- Does not appear in the ToC or outline.
- Is not assigned a heading level.
- Is just content within the list.

** Heading auto-leveling

Heading levels are not derived from list depth. They are derived from the heading hierarchy above the current item. Each ~=~ promotion looks up the tree for the most recent heading and adds one to its level.

#+begin_example
= Document Title                        ← H1
== Background                           ← H2
- = Project Alpha                       ← H3 (parent heading is H2)
  - Item A
  - = Goals                             ← H4 (parent heading is H3)
    - Item C
    - = Stretch Goals                   ← H5 (parent heading is H4)
  - = Timeline                          ← H4 (sibling of Goals)
- = Project Beta                        ← H3 (sibling of Alpha)
== Conclusion                           ← H2 (back to document level)
#+end_example

The writer never thinks about H-numbers. They just write ~- =~ and the hierarchy resolves itself from context.

** Standalone headings

For flat document-mode writing (no list structure), standalone headings use ~=~ at line start with depth by repetition:

#+begin_example
= Heading 1
== Heading 2
=== Heading 3
#+end_example

Multiple ~=~ symbols only matter in flat files where all headings are at the same physical margin. In indented structures, a single ~=~ is sufficient because depth is calculated from ancestry.

* Folding and Outline: Two Independent Features

Indue separates physical structure from meaning structure. Folding controls what is visible. The heading outline controls how meaning is organized.

A note on slot types. Sockets create slots (the blocks that hold content), and there are two kinds: heading slots and list slots. Heading slots are foldable and participate in the table of contents. List slots fold based on physical nesting, not heading level. The distinction matters because the same content can sit in either kind of slot depending on the socket that introduced it.

** Standalone heading folding (legacy/document behavior)

Standalone headings (~=~, ~==~, ~===~ at the document level, outside of any list) fold by heading hierarchy, consistent with the behavior users expect from Org-mode, Markdown editors, and word processors. A standalone heading folds everything until the next heading of equal or higher level.

#+begin_example
= Introduction                    ← folds until next =
Some paragraph text.
Another paragraph.

== Background                     ← folds until next == or =
More text here.

== Methods                        ← folds until next == or =
Even more here.

= Conclusion                     ← folds until next =
#+end_example

A standalone heading's fold scope includes any lists beneath it, folding the heading hides the entire list and everything inside it, as a single unit.

** List folding (physical structure)

Inside a list, folding is controlled entirely by list structure. Every list item with children is foldable, fold it and its children hide. This is determined purely by indentation or dash depth. Heading promotions (~- =~) inside lists have *zero impact* on folding. A heading-promoted list item folds because it is a list item with children, not because it carries a heading.

#+begin_example
= Methods                        ← standalone heading, folds by hierarchy
- = Data Collection               ← folds by LIST structure (has children)
  - Item A                        ← list child
  - Item B                        ← list child
  - = Analysis                    ← folds by LIST structure (has children)
    - Sub item                    ← list child
- = Results                       ← folds by LIST structure (has children)
  - Finding 1                     ← list child
#+end_example

In this example, folding "Methods" (a standalone heading) hides the entire list underneath it. But within the list, folding "Data Collection" hides only its children (Item A, Item B, and the Analysis section). The ~=~ on "Data Collection" and "Analysis" has no effect on folding, those items fold because they have child list items beneath them.

** Heading outline (meaning structure)

The heading outline is a separate navigational view showing only ~=~ promoted items. It provides a table of contents and jump-to navigation. The outline includes both standalone headings and heading-promoted list items. Headings can be folded independently within the outline view.

The outline concerns itself with meaning: what the document is about, how ideas relate hierarchically. It does not control physical folding.

** The handoff rule

The recommended behavior for applications:

1. Standalone headings fold by heading hierarchy (legacy behavior).
2. The moment a list begins within a heading's scope, list structure takes full control of folding.
3. Heading promotions inside lists are visible in the outline/ToC but are invisible to the folding system.
4. Folding a standalone heading hides everything inside it, including any lists, as a single unit.

These features never conflict because they serve different purposes. A list fold says "hide this content." A heading outline says "show me the structure."

A document without any ~=~ headings is still fully foldable, it is lists all the way down. A flat document with only standalone ~=~ headings still has a navigable outline. The two features are completely orthogonal.

** Invisible markers for prose-style documents

Using a schema declaration, list markers can be made invisible:

#+begin_example
:list<[]>::
- = Introduction
  This looks like body text under a heading.
  No visible bullet. Just indented prose.
  - = Background
    More body text.
  - = Methods
    And more here.
- = Conclusion
  Final thoughts.
#+end_example

Folds naturally from list structure. ToC comes from heading promotions. The source looks like a conventional document but has full outliner capabilities.

* Content Ownership

** The core rule

Content belongs to the most recent socket above it. There is no trailing child content, you cannot "return" to a parent level with content. To place content at a parent level, create a new socket at that level.

This rule applies in both indented mode and dash-mode. It eliminates an entire class of ambiguity that plagues Markdown, CommonMark, and Org-mode implementations.

** The ~:of<>~ escape hatch

In rare cases where content genuinely needs to attach to an ancestor, the ~:of~ spell explicitly reattaches content to a named station:

#+begin_example
- = Project Alpha ^alpha
  - = Goals
    - Item A
    - Item B
  :of@<^alpha> This thought belongs to Project Alpha
#+end_example

This is rare, explicit, and uses existing spell/station syntax. No new concepts required.

** Multiline content shortcuts

Scrolls ~[]~ and conduits ~{}~ act as escape hatches for quick multiline content that does not want to manage indentation line-by-line. The opening bracket at the correct indentation level signals ownership:

#+begin_example
- Level 1
  - Level 2
    [belongs to
level 2 without worrying about indent]
    - Level 3 {
belongs to level 3 with *bold* and #tags}
- Level 1
#+end_example

Scrolls preserve content literally. Conduits parse their content with the full Indue grammar.

* List and Heading Schema Declarations

Two spells configure how structural markers render: ~:list~ sets the *symbols* used for unordered items, and ~:step~ sets the *stepping patterns* used for ordered items and headings. Both are declared on standalone lines, opened as shells, which keeps marker configuration off the first content line.

#+begin_example
:step[a)]::                ; ordered items step a), b), c)
:list<*>::                 ; unordered items use *
:step[I.].list<->::        ; both at once
#+end_example

Neither is named after the marker it configures. A spell named for a character would require knowing which character means which before the declaration could be read; ~:list~ and ~:step~ say what they do (see No spell is named after a symbol).

** Showing the pattern, not naming it

A stepping pattern is written as *an example of its first marker*, not as the name of a sequence:

#+begin_example
:step[A.]::                ; A., B., C.
:step[1.]::                ; 1., 2., 3.
:step[a)]::                ; a), b), c)
:step[(i)]::               ; (i), (ii), (iii)
#+end_example

This is deliberate. Someone wants ~[A.]~; they should not have to learn that ~A.~ is called "upper-alpha with a period" and then translate their want into a keyword. The example *is* the specification, and the parser infers the sequence and the punctuation from it.

Supported sequences include arabic numerals, upper and lower alphabetic, and upper and lower roman, in whatever punctuation the example shows.

** Depth chains

A pattern implies a whole *chain* of markers, one per depth, so a single value configures an entire subtree:

#+begin_example
:step[A.]::                ; A. at this depth, then that pattern's chain below
#+end_example

Each sequence has a conventional descent. Listing several values overrides the chain depth by depth, the first value applying at the depth where the declaration sits:

#+begin_example
:step<[A.] [a.] [A.] [a.]>::     ; alternating upper and lower alphabetic
#+end_example

*** The void continues a chain

A void ~[]~ in a chain means *ditto*: take the next step in the chain established by the most recent explicit value. Consecutive voids keep walking that chain.

If ~[A.]~'s conventional descent is A. → a. → I. → 1., then:

#+begin_example
:step<[A.] [] [] [i.]>::
#+end_example

gives:

#+begin_example
A. Depth 1
   a. Depth 2
   b. Depth 2
      I. Depth 3
      II. Depth 3
         i. Depth 4
#+end_example

Depths two and three follow ~[A.]~'s own chain; depth four is overridden explicitly.

A void in *first* position has no explicit value before it, so it uses the application's default for that depth and the chain continues from there. This is how you override a deep level while leaving shallower ones alone:

#+begin_example
:step<[] [] [i.]>::        ; defaults for the first two depths, roman at the third
#+end_example

*** Chains cycle

When nesting runs deeper than a chain is long, the chain cycles back to its start. Every depth therefore always has a defined marker, however deep an outline goes.

** Symbols for unordered items

~:list~ takes symbol values in a vessel, one per depth, using the same depth rules:

#+begin_example
:list<->::                 ; - at this depth and below
:list<- + *>::             ; - then + then * as nesting deepens
:list<🐵>::                 ; any character works
#+end_example

A void ~[]~ makes markers invisible, which is how prose-style documents keep outline structure without visible bullets:

#+begin_example
:list<[]>::
- = Introduction
  This looks like body text under a heading.
#+end_example

** Scoping

Both are shells, so a declaration applies until it closes. A shell opened at a socket's block-start position auto-closes when structure outdents past that socket's depth (see Shells), so a declaration at the top of a list covers that list's whole subtree with no explicit close. Opening a new declaration of the same kind deeper in the tree makes it innermost; when its subtree ends, the outer declaration is in effect again:

#+begin_example
:step[I.].list<*>::
+ = Meeting Notes                     ; renders as: I. Meeting Notes
  :step[A.]::
  + = Action Items                    ; renders as: A. Action Items
  + = General Notes                   ; renders as: B. General Notes
    - = Ticket Audits                 ; renders as: * Ticket Audits
      - Common Scenario               ; renders as:   * Common Scenario
    - Uncommon Scenario               ; renders as: * Uncommon Scenario
+ = Other Topics                      ; renders as: II. Other Topics
#+end_example

The inner ~:step[A.]~ opens inside "Meeting Notes" and auto-closes when that subtree ends, so "Other Topics" sees the outer ~:step[I.]~ again. An explicit ~::step~ closes a declaration early.

Because the first value applies at the declaration's own depth, the same declaration can be reused at any depth and will do the right thing. There is no absolute depth numbering to keep in sync.

** User-typed markers

Where a stepping pattern is in effect, markers may also be typed directly, which keeps the source readable:

#+begin_example
:step[a)]::
a) hello
b) what's up
c) yeah
#+end_example

The parser matches these against the declared pattern at line start and treats the typed marker as a hint, correcting the sequence if it is wrong. Renumbering by hand is never necessary.

* Entity Configuration

Configuration binds a chain of spells to a *target set*, and it is where a reusable, named bundle of spells is defined. This is Indue's answer to "supertags": a target like ~<#project>~ can carry formatting, task defaults, or any spell to every reference it matches.

The word "indue" names both the language and the act of bestowing properties.

** Form: the ordinary spell grammar, laid out vertically

Configuration is not a separate construct. It is the ordinary spell grammar (see Spells) written across several lines, which is the readable layout when a target carries more than one or two spells:

#+begin_example
<#project>
.bg<#f0f0f0>
.stroke<1>:

Inline, the same thing on one line:
<#project>.bg<#f0f0f0>.card:
#+end_example

The chain follows the multiline-chain rules from the Spells section: a line beginning with ~.~ continues the chain, and the wall ~:~ terminates it. This layout is called a *cauldron* when it is used this way, but it is the same grammar as any inline spell, not a construct with its own delimiters.

A configuration chain of this kind is a *declaration*, not content. It lives between blocks and contributes nothing to the rendered body, the same as a whisper.

** What the target can be

Everything a configuration chain can target is a set (a set of one is not special). The target determines what the chain applies to:

| Target        | Matches                                              |
|---------------+------------------------------------------------------|
| ~<project>~     | every rendered form of the entity ~project~ (~#~/~@~/~^~) |
| ~<#project>~    | only the ~#project~ tag form                           |
| ~<@project>~    | only the ~@project~ mention form                       |
| ~<^project>~    | only the ~^project~ station form                      |
| ~<^project>~   | the place anchored by the station ~project~           |
| ~<#>~           | every sigil                                          |
| ~<@>~           | every signet                                         |
| ~<=>~           | every heading (a type/marker target)                 |
| ~<*>~           | the ~*~ glamour (configure what bold does)             |
| ~<:name>~       | *defines the spell (class) ~:name~*                    |

*** Type targets

A marker in the target selects a category: ~<=>~ all headings, ~<==>~ level-2 headings, ~<->~ unordered items, ~<#tag>~ a specific sigil. Granularity is marker plus optional depth plus optional name, and no further: no descendant or sibling combinators. Familiar word aliases (~h2~ for ~==~, etc.) are a fixed, spec-level synonym table resolving to the canonical marker; they are aliases, not a parallel selector language.

*** Nature decides the tier

A chain lands on the tier its spells belong to, not on whatever the target happens to render as:

- ~#~, ~@~, and visible ~^~ style their rendered expression (the tag, the mention, the span).
- A source renders nothing, but what an effect lands on is still decided by the spell's nature, not by the reference.

To style a block, use a block-natural spell; to style an inline expression, use a span-natural one. The target says *where*; the spell says *what kind of thing* is painted.

** Defining a class (~<:name>~)

A leading ~:~ inside the target means the target is a *spell*: you are defining (or extending) the spell ~:name~. This is consistent with ~:~ meaning "spell" everywhere. It is the reusable-named-style primitive, the CSS class:

#+begin_example
<:card>
.bg<#fff3cd>
.border<#ffc107>
.pad<2>:
#+end_example

~:card~ is now a first-class spell, usable exactly like a built-in:

#+begin_example
<project>.card           ; apply at a target
<x>.card.bold            ; compose in a chain
::card:: ... ::card      ; apply over a region (shell)
#+end_example

Rules for class definitions:

- The body is a *declaration chain*. It carries no *construct* target, since the target is supplied when the class is applied, but sub-spell targets (~@~) are allowed and are how a class reaches its own internal parts.
- A defined class is a first-class spell everywhere, inline, in chains, as a shell.
- Defining a name that collides with a built-in spell is rejected or warned, so a user cannot accidentally clobber ~:bold~.
- ~<name>~ (no colon) selects the *entity* ~name~; ~<:name>~ (colon) defines the *spell* ~name~. The single ~:~ is the whole distinction.

A class need not be elaborate. Pinning one input is a perfectly ordinary use, and often the most useful:

#+begin_example
<:rust>.code<rust>:        ; :rust[...] is now a Rust code block
#+end_example

*** A class may embed content, before its target

An embedding spell in a class body produces content each time the class is invoked. Since a class body is a chain, and a chain is ordered, the embed renders at its position:

#+begin_example
<:smart-tips>
.embed[= Smart Tips]
.card
.bg<#f0f7ff>
.bold@<=>:
#+end_example

#+begin_example
{
- tip one
- tip two
}.smart-tips
#+end_example

The card is framed, the heading is rendered inside it, and the tips follow.

*Content is embedded before the target, never after.* The target arrives at invocation, after everything the definition wrote, so there is no position after it for a definition to occupy.

That is a real limit, and it is the right one. Allowing content after the target would need either *placeholders* naming the target that has not arrived yet, which is formal parameters by another name, or *call-site ordering*, where the same class means different things depending on which shape invoked it and the definition can no longer be read on its own. Both cost more than a footer is worth.

Where content genuinely belongs after, wrap it:

#+begin_example
:figure.{
{tips}.smart-tips
Source: the handbook
}
#+end_example

Headers, badges, labels, and icons are what this covers, and they are most of what a themed block wants.

*** Spell packs

Because a class definition is just a declaration, a file of them is a *spell pack*: a shared vocabulary that any document in the same Lair can use. Beacon the definitions and they join the public layer; nothing further is required, and no application needs to know the pack exists.

#+begin_example
; languages.indue, in a Lair
!<:rust>.code<rust>:
!<:python>.code<python>:
!<:zig>.code<zig>:
#+end_example

This is how Indue's vocabulary grows without the specification growing. A pack is plain text, so it is portable and inspectable; an application that has never seen it still parses documents that use it, degrading unknown spells to their targets; and conflicts resolve under the ordinary cascade. Extending the vocabulary therefore does not fork the format, which is the usual pressure that splinters a markup language.

** The default cascade

Indue does not resolve styles by CSS-style specificity, comparing every rule against every object at once. It resolves a *running default* by document position, with per-object overrides as local exceptions. This is what lets the parser render each line from state accumulated above it, in a single downward pass (see Parser Architecture Notes).

*** Type-selectors set a running default

A bare type-symbol selector, ~<=>~ for headings, ~<^>~ for blocks, ~<#>~ for sigils, ~<*>~ for the bold glamour, and so on, sets that type's *default from its position forward*. A bare marker with no name is the type-selector; a marker with a name (~<#project>~) or a specific station (~<^section>~) is more specific.

Overriding a default happens two ways, and they behave differently:

- *Change the default* with a later type-selector of the same type. This is *persistent and forward-propagating*: everything after it uses the new default. Setting ~<^>~ to blue, then later to green, means blocks after the second selector are green.
- *Override one object* with a station target (~<^section>~) or an inline spell at the object. This is *local and non-propagating*: only that object changes; the running default is undisturbed, and the next object returns to whatever default is in effect at its position.

An object's look, when not individually overridden, is the default in effect *at that object's position* in the resolved (post-hoist) parse.

*** Hoisting sets the base before the body

Configuration can be *hoisted*, run once at the top before the body, established as the base default. A satchel is hoisted; individual config can be hoisted by placement. Hoisting *moves* rather than clones: the hoisted text runs once at the top, and on the downward pass its original position is inert (it does not re-fire or reset anything there).

*Hoisting preserves document order.* As the parser streams down, each hoisted block is appended to an accumulated hoist state, and that whole state is then run as setup before the body. Hoisted config therefore resolves the same way everything else does: later in the document wins.

This matters more than it might appear. Every other cascade in the language reads in one direction, and a reader who has learned "later shadows earlier" should never have to reverse that when looking at setup. One direction, everywhere.

Inline config met during the body still overrides the hoisted base from its position forward, since the hoisted state is established before the body is read.

** Scope and persistence

Codex effects are applied to the current block and forward. If a codex appears in the middle of a document, blocks above it are not affected.

#+begin_example
- Regular block #project             ; no codex yet, default styling

<project> .bg<#f0f0f0> :

- Styled block #project              ; inherits bg from codex
- Another styled block #project      ; also inherits
#+end_example

A later codex for the same entity overrides the previous one:

#+begin_example
<project> .bg<#f0f0f0> :

- Block A #project                   ; light gray

<project> .bg<#ffffcc> :

- Block B #project                   ; light yellow (overridden)
#+end_example

** Beacons and the public layer (~!~)

By default, a codex configures only the file it appears in. The *beacon* (~!~) prefix promotes a codex into a shared *public layer* visible to other files:

#+begin_example
<project> .bg<#f0f0f0> :        ; file-local: only this file sees it

!<project> .bg<#f0f0f0> :       ; public: other files in the vault see it
#+end_example

The beacon attaches to the cauldron as a whole, in both inline and multiline forms, and may also prefix a satchel to publish everything inside it. A cauldron is the unit of beaconing: its accumulated spells are public together or private together.

Beacons govern *codex* visibility only. Entities (sigils, signets, stations) are public by default and unaffected by the beacon. Content and spell invocations at content sites are always local and are never exported by it.

This is a *latent compatibility device*. An application that deals in single documents can parse and preserve the beacon without acting on it, nothing in a single file changes meaning because of it. Applications that do implement multi-document collections use it as the promotion mechanism; the full visibility model, vault scoping, and import/export rules are specified in the *Indue Vault Specification*.


** The satchel (~)

To hoist configuration to the top of the document (like HTML's ~<head>~ or a CSS style block), use a *satchel*. A satchel is a block delimited by ~ characters that is evaluated before the body text, regardless of its physical position in the file.

*** Satchel syntax

Any sequence of one or more ~~ characters acts as a satchel delimiter. Multiple ~~ characters in a row are treated as a single delimiter , ~\~\~\~\~\~~ is the same as ~~~. This allows visual decoration:

#+begin_example
~~~~~~~~~~
<project>
.bg<#f0f0f0>
.stroke<1>:

<meeting>
.bg<#e8f4fd>
.callout:
~~~~~~~~~~

= Project Alpha ^project
Content here automatically gets the project styling.

- Team sync #meeting
  This gets the meeting styling.
#+end_example

*** Header, middle, and footer satchels

Satchels can appear anywhere in the document, and because hoisting moves them to the top regardless, position is a question of readability rather than effect.

#+begin_example
Footer satchel (idiomatic ; no closing needed, terminates at end of file):
= Title
Content begins immediately.
More content...
~~~~~~~~~~
Configuration here ; no closing ~ required at end of document.

Header satchel (explicit ; useful when setup is the point):
~~~~~~~~~~
Configuration here
~~~~~~~~~~
= Title
Content.

Middle satchel:
= Part One
Content...
~~~~~
More configuration
~~~~~
= Part Two
#+end_example

*The footer form is the idiomatic one.* Open a satchel near the bottom with a run of ~~~ as a visual divider, put the document's configuration below it, and leave it unclosed: it terminates at end of file on its own.

Two reasons. A document should open on its content, so that someone reading it in a plain editor meets the title and the first paragraph rather than a wall of setup. And configuration is written rarely and read rarely once it settles, so it belongs where it will not be scrolled past every time the file is opened.

Because hoisting runs a satchel before the body wherever it sits, a footer satchel configures the whole document exactly as a header one would. Nothing is given up.

*** Satchel evaluation order

1. Applications scan all files in the vault scope.
2. Satchel contents are hoisted and evaluated before body parsing within each file. Where a file has several satchels, they run in document order, so a later one shadows an earlier one.
3. The body is then parsed with full knowledge of all codexes.
4. Inline codexes (not in satchels) override hoisted ones when encountered in document order.

By default, satchel contents are *file-local*, they configure only the file that contains them. To make a satchel's codexes available to the rest of the vault, mark it with a beacon (~!~). See "Beacons and the public layer" below, and the *Indue Vault Specification* for the full visibility model. Application developers should document their vault scanning behavior, including how cross-file public layers are surfaced.

*** Beacons on satchels (~!~)

A satchel prefixed with ~!~ is a *beacon satchel*, its contents join the vault's public layer and are available to every other file in the vault (modulo vault scope and import/export rules, specified in the *Indue Vault Specification*). This is the common pattern for vault-wide configuration:

#+begin_example
!~~~~~~~~~~
<project>
.bg<#f0f0f0>
.card:

<meeting>
.bg<#e8f4fd>
.callout:
~~~~~~~~~~
#+end_example

The leading ~!~ before the opening delimiter promotes the entire satchel to the public layer. Without ~!~, the same satchel would configure only the file it lives in.

Inside any satchel, beaconed or not, individual cauldrons may also carry their own beacon. A non-beacon satchel can still expose specific codexes by beaconing them individually:

#+begin_example
~~~~~~~~~~
<private-style>
.bg<#fff>:                   ; file-local

!<project>
.bg<#f0f0f0>
.card:                       ; public, despite the satchel being private
~~~~~~~~~~
#+end_example

Per-codex beacons inside a beacon satchel are redundant but harmless , the satchel-level beacon already promotes everything inside.

** Codex for stations

Place a station above its cauldron to make the definition itself navigable:

#+begin_example
^project
<project>
.bg<#f0f0f0>
.card:
#+end_example

Now ~@project~ jumps to the codex definition. The codex is its own documentation.

** Interaction with the configuration hierarchy

All cauldrons compose by the specificity order given above:

- *Type/marker selectors* (~<=>~, ~<#>~, ~<*>~), how a category renders.
- *Entity identity* (~<project>~), shared across every form of one entity.
- *Form-specific* (~<#project>~, ~<@project>~, ~<^project>~), scoped to one form.
- *Inline spells* (~<x>.bg<red>~), one-off overrides in place.

More specific wins; inline beats named beats type; explicit beats inherited; last-write-wins on ties.

** Entity namespace and its boundary

Every form of a name, ~#name~, ~@name~, ~^name~, and the block handle ~^name~, resolves in *one shared namespace* (see the role matrix in Stations). A cauldron defined for ~<name>~ applies to every rendered form; the form communicates intent (tag, mention, anchor, block), not scope.

The namespace boundary is the *vault*. Names resolve vault-wide: a station or entity named in one file is reachable from a reference in another file of the same vault. Collisions produce a set (set semantics); navigation to a multi-member set is a disambiguation the app surfaces. The unique machine handle is the disambiguator of last resort. Cross-vault resolution happens only through the explicit import/export rules in the *Indue Vault Specification*.

** Open questions for entity configuration

- If a block carries several entities (~#project~ and ~#urgent~), do both cauldrons apply, and in what order? (Likely: in the order the entities appear, last wins on conflict, per the specificity rule.)
- Should there be an intersection selector, a cauldron that fires only when two entities are both present?

* Parser Architecture Notes

** Three-phase evaluation

Indue is designed to render each line from the state accumulated above it, with the minimum number of passes. Evaluation is three phases:

1. *Build the default property list for every object type.* Before reading the document, initialize the default look of each type (block, heading, list item, sigil, signet, station, each glamour) to its built-in default. This is the starting state the rest of the parse mutates.
2. *Stream down and collect hoists.* Read top to bottom; when a hoisted block (a satchel, or config marked for hoisting) is seen, append it to the hoist state. Hoisting moves rather than clones: the block runs once as setup, and its original position is inert on the downward read. Appending preserves document order, so later hoists shadow earlier ones, matching every other cascade in the language (see The default cascade).
3. *Read top to bottom and render each line as the state shows it.* With the base defaults established, stream the body. Each type-selector reassigns its running default from that point forward; each per-object override applies locally without disturbing the running default; each line is rendered against the state in effect *at that line*. Nothing looks ahead or backtracks, because every value a line needs, defaults, referenced node values (which resolve at parse position), current property state, comes from what has already been read above it.

Phases 1 and the setup part of 2 can be folded into the single downward read, so the expensive work is one streaming, stateful pass. This is the whole reason the language forbids forward references and resolves everything against upward state.

** Three-layer grammar

The formal grammar should be defined in three distinct layers, preceded by a lexical pre-pass:

0. *Whisper pre-pass*: strips comments before the layered grammar runs. On each line, the first unescaped ~;~ that is *not* inside a scroll ~[]~ begins a whisper; the whisper and everything after it on that line is discarded. Semicolons inside scrolls are literal, and a nick-escaped ~\;~ is a literal semicolon. The count of consecutive semicolons (~;~/~;;~/~;;;~/~;;;;~) carries no parser meaning, all whisper levels strip identically; the count is a convention for human readers and optional tooling (folders, outline views) only.
1. *Socket layer*: identifies list items, heading promotions, and stations. This is line-start based (sockets begin the line). Sockets are parsed first, and spell and glamour parsing follows.
2. *Glamour layer*: identifies inline formatting (bold, italic, underline, strikethrough). These follow the untargeted, single-word, paired, and bracket rules. Stacking and symmetric nesting rules apply.
3. *Entity layer*: identifies signets (~@~), spells (~:~), sigils (~#~), stations (~^~), and container content (vessels, scrolls, conduits, target containers). A vessel glued to a spell is an input. ~<>~, ~{}~, and ~[]~ open spell world on sight and are targets; a bare word is a target only when glued directly to a wall. Spell world ends at whitespace outside a container, at an unbonded line break, or at a closing wall. The sigil form communicates intent (tag, mention, anchor) but not scope. A spell's nature decides whether a block or a span is painted; the target only says where.

Because scrolls suppress whisper detection, the pre-pass must be scroll-aware rather than a naive line split: it scans for ~;~ while tracking whether it is currently inside an open scroll on that line.

Goety is matched in the entity layer, before container parsing, as fixed whole patterns rather than as compositions of scrolls and vessels. Because adjacent containers carry no meaning outside a spell, these patterns cannot collide with ordinary syntax. The block-start checkbox forms are matched before a leading scroll would be read as an embed, which is what lets ~[]~ mean an open task there and an empty scroll elsewhere.

** Indentation handling

List nesting and content ownership in indented structures are determined by physical indentation. Both tabs and spaces are accepted; the parser normalizes to indent levels. The specific number of spaces per level does not need to be consistent, only the relative depth matters (Option C: strictly deeper than the parent socket).

** Heading level logic

Heading levels are derived from the heading hierarchy, not from list depth. Each ~=~ promotion looks up the tree for the most recent heading and adds one. In flat document mode, the count of ~=~ symbols determines level directly.

** Stateful list parsing

A schema declaration (~:step[a)]::~) is an ordinary shell, opened at a socket's block-start position. It pushes onto the same shell stack as any other shell, keyed by which spell opened it. No separate mechanism is needed: the shell auto-closes when structure outdents past the depth at which it opened (see Shells), which pops it from the stack, and the next enclosing declaration of the same kind, if any, is in effect again.

** Block handles in the AST

~^name~ (station) values are stored as a property of the block node, not as a child of the text content. This allows apps to look up ~node.id~ directly without traversing the text.

** Error recovery

- Unclosed glamours apply to the single word they touch, or render as literal text if not adjacent to a word.
- Unknown spell names render their conduit/scroll content as plain text.
- The parser never throws errors to the user.
- Strict validation belongs in the linter and export pipeline.

* Relationship to Typst

| Feature         | Typst               | Indue              |
|-----------------+---------------------+--------------------|
| Function prefix | ~#~                   | ~:~ (spell)          |
| Tag syntax      | ~#tag("work")~ (func) | ~#work~ (sigil)      |
| Headings        | ~=~ / ~==~ / ~===~        | ~=~ / ~==~ / ~===~       |
| Bold            | ~*text*~              | ~*text*~ (same)      |
| Italic          | ~_text_~              | ~/text/~ (glamour)   |
| Underline       | None built-in       | ~_text_~ (glamour)   |
| Strikethrough   | None built-in       | ~%text%~ (glamour)   |
| Checkboxes      | None (package/show) | ~:o~ ~:x~ (spell)      |
| Task states     | Convention          | Native spells      |
| Lists           | ~-~ / ~+~               | ~-~ / ~+~ (same)       |
| Labels          | ~^label~              | ~^label~ (station) |
| References      | ~@ref~                | ~@ref~ (signet)      |
| Error handling  | Strict compiler     | Parse, don't fail  |

** Transpilation to Typst

- ~=~ headings pass through (same syntax).
- ~:func<...>~ (spell) becomes ~#func(...)~.
- ~#tag~ (sigil) becomes ~#tag("tag")~ (via a Typst package).
- ~:o~ / ~:x~ become ~#todo~ / ~#done~ (via a Typst package).
- Bold and lists pass through unchanged.
- ~/italic/~ becomes ~_italic_~.
- ~_underline_~ becomes ~#underline[...]~.

** Typst is the typesetting path

Indue has no layout mechanism and does not plan one (see Single-column renderability). Tables are as close as the core comes, and they are a single block-level construct rather than a layout primitive.

For work that genuinely needs page geometry, columns, page breaks, floats, precise typography, the recommended path is to export to Typst once tooling exists, rather than for Indue to grow a competing layout model. This keeps Indue portable across applications that cannot render layout at all, while leaving real typesetting to a tool built for it.

* Compliance

Indue compliance is binary. An implementation either supports the full semantic core of the language or it doesn't. There is no tiered checklist , the semantic features that make Indue distinct from Markdown are not optional extras.

** Core

The complete semantic foundation. An application claiming Indue compatibility must support all of the following:

*Lexical*
- Whispers (comments): ~;~ to end of line, stripped in a scroll-aware pre-pass. Literal ~;~ inside scrolls ~[]~ and via the nick (~\;~). Graduated levels (~;~/~;;~/~;;;~/~;;;;~) strip identically; level is a reader/tooling convention, not a parser distinction.

*Structure*
- Sockets: ~-~, ~+~, ~=~ with indentation-based and dash-mode nesting
- Heading promotion: ~- =~ / ~+ =~
- Schema declarations: ~:list~ and ~:step~, with void ditto and cycling depth chains
- Folding and heading outline

*Glamours*
- All five (~*~, ~/~, ~_~, ~%~, ~`~) expand to spells: a single glamour is ~:spell:~, a pair is ~:spell.{~ … ~}:~
- Untargeted, grab-rule, paired, and bracket forms
- Runs of one repeated character collapse to one; a run stops when the character changes
- Stacking different marks requires a bracket immediately after the run
- Glamours are glued and inline; regions across lines are shells

*Goety*
- The closed set: ~[label](url)~ and ~[]~ / ~[ ]~ / ~[>]~ / ~[x]~ at block start, each matched as a fixed whole pattern
- Block-start checkbox forms map directly to the three lifecycle values, not through the alias spells

*Entities*
- Sources: ~&name&~, shadowing for resolution, properties accumulating across declarations, repeated keys forming a history with latest-wins on read
- ~|version~ as authored shorthand for a ~version~ property, and as a selector on any mark
- Shared namespace: ~#~ goes to the station, ~@~ to the source, ~^~ to the marked spot
- Signet resolution must not depend on an application-built index
- Sigils: ~#tag~ (including multi-word and whole-line)
- Signets: ~@ref~
- Stations: ~^name~ with trails (undefined, portals, defined, terminated), aliases, last-write-wins; always visible
- Cauldron matching matrix: entity name × sigil form (~<name>~, ~<#name>~, ~<@name>~, ~<^name>~, ~<^name>~, ~<#>~, ~<@>~, ~<=>~, and ~<:class>~ definitions)
- Cauldron bestowal escalation: three-colon paints inline tokens by and the spell's nature selects block or span ( ~#~/~@~/~^~ select their rendered expression)
- Entity codex cascade: form-only → identity → form-specific → inline

*Spell system*
- Bond: ~.~ chaining
- Shell: a colon run opening a region of effects, opened by a spell chain or a glamour run
- Closer length must match opener length; a bare closer closes all shells of that length; a glued closer stops one effect in the innermost shell where it is active
- A shell closes when it has no active effects left
- Structural auto-close when opened at a socket's leading position, and auto-close at end of document
- Hypershells: a run of three or more, length-matched, with the closer alone on its own line, for content Indue must not read
- Spell world: entered by ~:~ or by a container (~<>~, ~{}~, ~[]~); vessels ~()~ never open it
- Spell world ends at whitespace outside a container, at a line break with no glued bond following, or at a closing wall ~:~
- Vessel ~<>~: value arguments when glued, targets when bonded; ~@~ narrows a target to one spell
- Reach: block spells deep, span spells shallow, with ~:deep~ and ~:shallow~ to set either tier explicitly
- The grab rule: a bare word glued to the right of a spell is its target; this is the only undelimited target position
- ~:strip~ resets inherited properties; ~:strip<:name>~ narrows to one
- Target roles are lexical: a container glued to a spell name is an input, a bonded container is a construct target, and an ~@~-marked container confines that slot's direct effect; a bare word target uses the grab rule
- A marked slot narrows what it does, not what reaches its target; the target is still covered by the construct's own targets if it falls within them
- Spell slots: the unit between bonds, each carrying its own spell, inputs, and optional target
- Both shapes: spell-first (cast) and target-first (offering), producing identical results
- A class may embed content before its target, never after
- Per-spell targets: ~@~ narrows a target to the preceding spell; adjacent summons on one spell are additive
- Three effect categories: styling, data, embedding (any combination)
- Generated targets: an embedding spell supplies its own target, so its other effects apply to the generated content
- Paint forward: a spell with no target applies its properties to the end of the enclosing scope
- Spell blocks: a block whose only rendered content is one spell's target; a positional fact, with presentation left to configuration
- Astral blocks: a spell with no material content to grip passes its effects to the enclosing scope; between blocks that is the document
- Trailing whitespace elision for spells with no target and no embedding effect
- Inputs: at most one of each kind, vessel ~()~ plus either scroll ~[]~ or conduit ~{}~, identified by bracket rather than position so order is free; two containers of the same kind are invalid
- Multiline chain form (the cauldron layout)
- Maths: ~:math[...]~ with ~:$~ as an alias
- Nick: ~\~ escaping
- Parse-don't-fail error recovery

*Task model*
- ~:task~ with exactly three values: ~open~, ~active~, ~closed~. The set is closed; applications must not add a fourth
- Block tasks shadow; span tasks accumulate and do not determine their block's state
- Queries return each task separately, rendering span text or flattened block text
- The alias spells ~:o~ and ~:x~, shipped as definitions and not redefinable
- ~:>~ reserved and built in; no user-defined spell may take a name containing ~>~, since a vessel closes on it
- Custom states via ~<:name>.task<state>~, with ~.task~ mandatory so unknown vocabulary still resolves to a lifecycle position
- ~:cycle[name]<:a :b :c>~: named, ordered, enumerable; last declaration wins for both the cycle and for a state's membership
- Filtering by lifecycle state, resolving custom states through their declared ~.task~ value

*Scheduling model*
- Six separate axes: date, time of day, repetition, series bounds, exceptions, completion; no spell carries two
- One schedule per block: scheduling spells set block properties and shadow
- ~:completions~ binds by adjacency, on the task's line or the line below; application-maintained
- Recurrence patterns are a closed grammar with a fixed clause order, not natural-language parsing
- A pattern carries no date; the anchor comes from the date spell on the same item
- Every pattern maps to exactly one RRULE; export is deterministic and import is not

*Queries*
- ~:query~ takes a SQL query as a scroll, unparsed; the grammar belongs to the query language
- A query resolves *as if the whole Lair had been parsed*. Indexing and caching are free, provided results are identical to a full parse
- Node identifiers are deterministic for a given input, and are not stable across edits; durable identity comes from sources

*Entity configuration*
- Cauldron layout: target-first multiline chains, entity targets, type targets, and ~<:name>~ class definitions
- Satchel: hoisted configuration, file-local by default; several in one file run in document order, so a later one shadows an earlier one
- Beacon (~!~): parsed and preserved as a cauldron or satchel prefix

*Specified in the companion documents*

The catalogue of spells an implementation must support, task states, scheduling and recurrence, queries, transclusion, presentation spells, tables, and layout, is enumerated by category in *The Indue Spellbook*. Multi-document behaviour, the public/private visibility model, vault declarations and types, and import and export, is specified in the *Indue Vault Specification*. An application that handles only single documents is still compliant with this specification; it must parse and preserve the beacon, but need not act on it.

** Extensions

Extensions are renderer-specific or application-specific features built on top of the core. They use the ~:ext.*~ namespace and degrade gracefully in applications that don't support them. ~:ext.css~ is the canonical reference extension; both are specified in *The Indue Spellbook*.

Layout belongs to extensions entirely, not to core. Container geometry (grid, flexbox, columns, absolute positioning, page-constrained layouts, animations) is ~:ext.css~ territory, because none of it survives the single-column rule (see Single-column renderability). Core has no layout mechanism at all; tables are the only construct with internal columns, and they occupy one block-level slot.

The compliance story is simple: does it do the full semantic core? If yes, it is Indue-compatible. If no, it is at best Indue-aware, a stepping stone, not a destination. There are plenty of Markdown renderers for basic formatting. Indue exists because tasks, scheduling, and linking deserve first-class treatment.

* Open Design Questions

** Selecting by position

A *spell block* is a defined position (see Spells), but there is no selector syntax yet for targeting it: a rule that applies to ~:code~ only when it forms a spell block, and not when it appears inline. Shipped defaults need this to express conventional block presentation, and documents need it to override them.

** Term/definition lists

~/~ is used for italic, so Typst's ~/ term: definition~ is not available. The leading candidate is a spell like ~:def<term>{definition}~. A bare delimiter character is harder to find now that ~;~ has been claimed for whispers (comments) and ~&~ remains the main unreserved punctuation; a spell form avoids consuming scarce single-character real estate.

** Document-level metadata and frontmatter

How should *document-level* metadata (title, author, date) be represented? A YAML-style frontmatter block, a dedicated ~:doc~ spell, a satchel-hosted ~<doc>~ codex, or something else?

Note that *per-entity-instance* metadata (e.g., distinct styling for ~@alice~ versus ~@bob~ when both appear on the same block) is resolved by cauldron targeting: each reference token carries its own codex independently of its neighbors, and the surrounding block stays untouched unless a block-natural spell is used. Only the document level remains undecided.

** Scripting and logic

Should Indue have scripting, or should logic live in host tooling?

** Named spell arguments

Currently positional only. Named arguments may be added if needed.

** Escaping edge cases

The nick (~\~) serves as a general escape character (e.g. ~\*~ for a literal asterisk, ~\#~ for a literal hash, ~\;~ for a literal semicolon that should not begin a whisper). The full set of characters that need escaping in various contexts should be specified precisely. In particular: which characters need escaping inside scrolls (probably none, since scrolls are literal, including ~;~ which is never a whisper there), inside conduits (where ~;~ does begin a whisper), and in plain text at line start vs mid-line.

* Implementation Requirements

Building Indue as a real language requires:

- A formal grammar specification (likely PEG or context-free), defined in three layers: socket, glamour, and entity.
- A Rust reference CLI as the canonical implementation.
- Error handling with clear diagnostics (for the linter/export pipeline; the core parser follows parse-don't-fail).
- A tree-sitter grammar for editor syntax highlighting and structural queries.
- A transpiler to Typst for typeset PDF export.
- Unicode handling (UTF-8 throughout).
- A comprehensive test suite covering nesting, ambiguity, edge cases, and round-trip fidelity.
- Documentation of every syntactic interaction and edge case.
- A Flutter/Dart application (OUST, name pending) consuming the Rust implementation via Flutter Rust Bridge, targeting MechanixOS, Android, iOS, and desktop Linux.
- A vault scanner that locates ~.vault~ markers, builds the public layer for each vault, applies import/export overrides, and exposes the resolved namespace to consuming tools. Galleries should be processable as a separate prior pass to enable caching of hermetic public layers.
- Permission-aware filesystem traversal: graceful handling of read failures, clear surfacing of write failures, and explicit reporting of unreachable files rather than silent omission.
